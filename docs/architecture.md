# Architecture

Status: Draft — under founder review
Companion: [product.md](./product.md)

## 1. Design principles

1. **The product is the run pipeline.** Engineering effort goes to the pipeline, provenance, and verification; the UI exists to run the pipeline and review its output.
2. **Declarative definitions.** The listing launch service and each market profile are versioned, schema-validated definition files. A new market is a new profile; a new service is a new definition.
3. **Deterministic where possible, models where necessary.** State transitions, claim-source validation, number checks, exports, and cost accounting are plain code. Models do perception, extraction, generation, and judgment.
4. **Measure, don't trust.** Every model call is logged with model ID, usage, latency, and estimated cost. Model behavior is checked by a seeded-defect evaluation set, not assumed.
5. **Human gates are state-machine states.** A run cannot advance past a gate without a recorded human decision.
6. **Standard mode only** for all calls that carry customer content; `-contributor` model variants are never used.
7. **Libraries before hand-rolled code.** When an established, well-maintained library solves a specific job, use it instead of writing raw HTTP or utility code. Native `fetch` or custom code is chosen only when the library would be disproportionately heavy (install size, runtime cost, transitive dependencies) for that job. Every dependency has one stated purpose.

Consequences of native type stripping for `apps/api` and `packages/shared`: only erasable TypeScript syntax (no `enum`, no parameter properties, no namespaces with runtime code), relative imports carry the `.ts` extension, type-only imports use `import type`, and tsconfig `paths` aliases are not available. The web app uses bundler resolution and is unaffected. The web app consumes `@evidomo/shared` as source without a build step: `transpilePackages: ['@evidomo/shared']` in `apps/web/next.config.ts` makes Next compile it and bundle it into the routes (so the web runtime image needs no shared sources), and `allowImportingTsExtensions` in `apps/web/tsconfig.json` lets the web type check follow its `.ts` imports. The web app's own imports stay extensionless.

Pages Router treats every file under `apps/web/src/pages` as a route, so web tests live in `apps/web/src/__tests__`.

Caddy routes `/api/*` to the API and everything else to the web app on the same domain, so cookies stay same-site and no CORS configuration is needed. In development the Next.js dev server plays that role: a rewrite active only under `next dev` proxies `/api/:path*` to `API_PROXY_ORIGIN` (default `http://localhost:4000`), so the browser stays on `http://localhost:3000`, the API's default `APP_ORIGIN`. Production builds carry no rewrite (`next start` answers 404 on `/api`; Caddy never sends it there).

## 4. Meta Model API integration

All model access goes through one `meta` module in `apps/api/src/meta`: client configuration, timeouts, usage capture into the ledger, and the record/replay switch used by tests. Retries (exponential backoff on 429/5xx, honoring `Retry-After`) use the SDKs' built-in retry settings; the module does not add a second retry layer on top. Both SDKs call the API over `fetch`, so MSW record/replay works the same for either.

Module interface (P1-01; details and measured shapes in [model-notes.md](./model-notes.md#p1-01--meta-client-module)):

- `createMetaClients({ apiKey, usage, estimateCost?, logger?, maxRetries?, timeoutMs? })` returns the AI SDK provider (`createOpenAI({ name: 'meta' })`, Responses models via `languageModel(id)`), the `openai` client, `aiSdkCallOptions()`, and `captureOpenAIUsage(call)`. The AI SDK has no provider-level retry/timeout settings, so every AI SDK call spreads `...aiSdkCallOptions()` (`maxRetries`, `timeout`, and the `onLanguageModelCallEnd` usage hook). The `openai` timeout is per attempt; the AI SDK timeout covers the whole call including retries.
- A shared fetch wrapper rejects any request whose `model` ends in `-contributor` (principle 6, enforced in code for both SDKs).
- Usage capture: `UsageRecorder.record(entry)` receives model ID, input/cached/output/reasoning tokens, latency, response ID, `estimatedCostUsd` from a pluggable `CostEstimator`, and, for non-token models, `audioDurationMs` (whole milliseconds, Voice) or `images` (Muse Image, SAM). `record` is synchronous because the AI SDK silently swallows errors thrown by its callbacks; the usage ledger (P2-04, §10) buffers and persists after the call returns. `estimatedCostUsd` is a float for display and logs only; the ledger persists an exact decimal computed from the units.
- Record/replay (`replay.ts`, test-only): fixtures in `fixtures/meta/<task>/<name>.json`, matched by method, path, and a hash of the normalized body; replay never touches the network and fails loudly on an unmatched request; `RECORD=1` records 2xx responses only and never stores request headers. Options added in P3-10: `extend` (record mode serves what the cassette already answers and writes back only the interactions the session used), `onInteraction` (a hook called before each response reaches the SDK), `match.imageAlias` (data-URL images hashed by a stable name instead of their bytes), and the counters `liveRequestCount` / `servedFromCassetteCount`.
- `MODEL_API_KEY` is required at boot in production and optional in development/test (replay tests use a placeholder).
- Per-call model settings (P1-02; [model-notes.md](./model-notes.md#p1-02--spark-13-text-vision-structured-output)): AI SDK calls pass `providerOptions: metaProviderOptions({ reasoningEffort, store? })`, `openai` SDK calls spread `metaResponsesParams(...)`. The helper exists because `@ai-sdk/openai` reads only the `openai` options key (options under `meta` are dropped silently) and drops `reasoningEffort` for non-OpenAI model IDs unless `forceReasoning: true`. Accepted efforts for Spark and Wonder (P1-03) are `minimal`, `low`, `medium`, `high`, `xhigh`, `max` (`none` is rejected); `metaReasoningEffortSchema` validates definition values. `store` defaults to `false` because steps carry customer content.
- Images (P1-06; [model-notes.md](./model-notes.md#p1-06--muse-image-edits)): `generateMetaImage(clients, { modelId, prompt, size?, outputFormat? })` and `editMetaImage(clients, { ..., images })` in `meta/images.ts` call the AI SDK `generateImage` on `clients.imageModel(id)` (which reaches `/v1/images/generations` and, with input images, `/v1/images/edits`), bound the whole call by the shared timeout, read the output size from the image header, and record usage through `clients.recordUsage(...)` with `images` set (Muse Image bills per image: `ImagePrice { usdPerImage }` in the estimator). Large base64 payloads in fixtures are stored as separate files in `fixtures/meta/<task>/<name>.files/`. Muse Image enables image search, web search, and shell unless `tool_enablement` turns them off; only the JSON edit body validates that field, so customer photos go through `editMetaImageToolsOff(clients, { modelId, prompt, image: { bytes, mediaType }, size, outputFormat, abortSignal? })` (P3-04): `openai.post('/images/edits')` with the JSON body and all three tools off ([P1-08](./model-notes.md#p1-08--muse-image-with-tools-disabled)). It records usage with `images` = returned images before validating them (the response has no `model`, so not `captureOpenAIUsage`), and throws `MetaImageEmptyError` for a 2xx without an image, `MetaImageResponseError` for another shape, and `ImageDecodeError` for non-image bytes. `editMetaImage` (AI SDK, multipart) is for synthetic inputs only. Text-to-image with the tools off is `generateMetaImageToolsOff(clients, { modelId, prompt, size, outputFormat, abortSignal? })`: `openai.post('/images/generations')`, whose JSON body validates `tool_enablement` the same way (P4B-01, used by the dev-only showcase image generator).
- SAM 3.1 (P1-05; [model-notes.md](./model-notes.md#p1-05--sam-31-and-output-parser)): `segmentImage(clients, { modelId, phrase, image, reasoningEffort, includeConfidence? })` in `meta/sam.ts` sends one noun phrase (validated: no lists or token characters) and one image through `generateText`, with `metaProviderOptions` plus `metadata: { mask_encoding: "one_bit", include_confidence: "true" }`. It records usage before parsing with `images` from the response's `usage.images_processed` (tokens are reported as 0), and returns `segments: { label, objectId, score?, box: { x0, y0, x1, y1 }, mask }[]`: boxes in source-image pixels, half-open; masks box-local `one_bit` rasters decoded by `decodeSamMask` (`meta/sam-mask.ts`), a wrapper over `@meta-sam/parser`'s `decodeMaskToRaster`. `parseSamImageOutput` (`meta/sam-output.ts`) rejects any deviation from the documented grammar with `SamOutputError`.
- Structured output uses `generateText({ output: Output.object({ schema }) })` (`generateObject` is deprecated in AI SDK 7) in strict `json_schema` mode, which Meta enforces server-side: output schemas use `.nullable()`, never `.optional()`.
- Voice Transcribe (P1-04; details in [model-notes.md](./model-notes.md#p1-04--voice-transcribe)): `transcribeAudio({ openai, usage, estimateCost? }, { model, mode, audio, keywords?, languageBias?, ... })` sends the multipart body (`request` JSON part + `audio` WAV part) through `openai.post` and returns `{ sessionId, text, audioDurationMs, turns: TranscriptTurn[] }`, `TranscriptTurn = { index, speaker?, text, startMs, endMs }`. Usage is recorded as `UsageEntry.audioDurationMs` (no tokens). Audio is converted beforehand by `apps/api/src/media/convert.ts` (ffmpeg → 16 kHz mono 16-bit PCM WAV, header verified).

The Vercel AI SDK is the primary client. The official `openai` package fills the gaps where the AI SDK does not reach an endpoint or changes its output. Native `fetch` is a last resort, used only if neither SDK can express a request.

Known API constraints the design depends on (from Meta's docs):

- **Voice Transcribe** file endpoint accepts only mono 16-bit PCM WAV at 16 or 24 kHz, max 32 MB and 10 minutes. Timestamps are turn-level only (`startMs`/`endMs`); there are no word-level timestamps. Keyword biasing is supported (no documented limit on count or length). Turn timestamps are the evidence anchors for transcript claims. Measured in P1-04/P2-06: turns exist only in `ENDPOINTING`/`DIARIZATION` mode (empty in the default `PUSH_TO_TALK`); on the same 2:49 TTS clip `ENDPOINTING` returned a single turn and `DIARIZATION` 15 turns of 2–16 s, so intake uses `DIARIZATION`; the transcript can repeat words ("12 12"), so transcript numbers are never cited directly.
- **SAM 3.1** takes one noun phrase per request; several object types mean several requests. Masks come back as special-token text that must be parsed (see the cookbook's `07_sam` recipes). SAM segments; it does not classify — classification is Spark's job.
- **Muse Image** edits do **not** accept a mask. The docs say edits keep the rest of the image intact but do not guarantee pixel preservation, and output dimensions may differ from the input. This is why the integrity check exists — and why its feasibility is verified in Phase 1 before staging is committed to.
- **Reasoning tokens are billed at output rates** ($20/1M on Wonder). Reasoning effort is therefore set per step, not globally.

Verified in Phase 1 against the pinned SDK versions (consolidated in [model-notes.md, Summary](./model-notes.md#summary)): the client column above, the transcription multipart body through `openai.post` (P1-04), reasoning-effort pass-through, structured-output behavior, and usage fields (P1-02: reasoning tokens are reported in `output_tokens_details.reasoning_tokens` and included in `output_tokens`).

**Gates:** Gate 1 (fact conflicts) after step 4; Gate 2 (claim audit and image approval) after steps 7–8.

**Intake (P2-06).** Code: `apps/api/src/pipeline/intake/` (`handler.ts`, `keywords.ts`, `turns.ts`), registered in `worker.ts`; measurements in [model-notes.md](./model-notes.md#p2-06--intake-step).

- **Input:** the project's single `ready` voice memo created before the run (none, several, a missing file, a checksum mismatch, invalid metadata, or a memo longer than the service's `max_seconds` fail the run with `NonRetryableStepError` before any model call). The stored WAV is read through `Storage` and sent as `voice-memo.wav` (a fixed name: no IDs leave the process). Model, `transcription_mode`, and `max_turn_seconds` come from the step configuration; the per-attempt HTTP timeout grows with the memo length (`max(180 s, 60 s + duration / 2)`). The call goes through `ctx.ledger.meter`.
- **Keywords** (`buildTranscriptionKeywords`, deterministic): (1) free-text fact-form values whose key is not a typed market fact (street and place names; typed facts are numbers, booleans, and enums), keys in code-point order; (2) the parenthesised local terms of the profile's fact labels (`Living area (woonoppervlakte)` → `woonoppervlakte`; lists are split); (3) the profile's `transcription_keywords`. Each term is NFC-normalized with whitespace collapsed, kept only with at least two letters (skips `A`, `A++`, house numbers) and at most 64 characters (longer text is skipped, not cut), de-duplicated case-insensitively (first spelling wins), and the list is capped at 50 in that priority order. Meta documents no limit; these bounds are ours (`TRANSCRIPTION_KEYWORD_LIMITS`). `languageBias` is the profile's source languages as English names (`nl, en` → `Dutch, English`). Keywords are never logged.
- **Turns** (`toStoredTurns`): trimmed, empty turns dropped, ordered by start time (diarized turns may overlap), indices `0..n-1`. A turn longer than `max_turn_seconds` (30 s in `listing-launch.v1`) is split at sentence ends (word ends if there are too few sentences) into `ceil(duration / max)` chunks whose start times are interpolated from their character offset, marked `timing: 'approximate'`; untouched turns are `timing: 'model'`. `sourceTurnIndex` keeps the API turn.
- **Output:** one `transcript` artifact (content: `transcriptArtifactContentSchema` in `packages/shared/src/transcription.ts` — material ID and SHA-256, model, mode, session ID, billed duration, the keywords and language bias sent, `maxTurnMs`, turns `{ index, sourceTurnIndex, speaker | null, text, startMs, endMs, timing }`) and a `transcript_stored` event with counts only (turns, approximate turns, speakers, keywords, duration). Both are written in `commit(tx)`. A turn's stable ID is `(artifact ID, index)`, which is what `facts.source_ref` cites (P2-07) and where playback starts (P4-06).
- **Why an artifact, not a turns table:** §8 already models transcript provenance as artifact ID + turn index; a transcript is written once and never edited per turn; consumers read it whole (P2-07 sends the full transcript to Spark, the evidence inspector loads one transcript of tens of turns); it cascades with the run and project like every other output and is replayed with the artifacts (§11). A table would add a repository and a join for no query we need.

**Fact extraction (P2-07).** Code: `apps/api/src/pipeline/extraction/` (`handler.ts`, `form.ts`, `normalize.ts`, `prompt.ts`, `schema.ts`), registered in `worker.ts`; measurements in [model-notes.md](./model-notes.md#p2-07--fact-extraction).

- **Form (no model call):** `factFormToCandidates` maps every market fact present in `projects.fact_form` to a candidate with the profile's unit (`units.area`, `units.volume`, `currency`) and basis (area facts only), `source_kind = form`, `source_ref = { field }`. `null`/absent means unknown. A missing required fact or a value that does not fit its type (enum value, non-negative number, integer in range, boolean) fails the run with `NonRetryableStepError` naming the keys only. Other form fields (street and place names until base property fields exist) become `other:<field>` facts when the key is a slug and the value a number, boolean, or short text; anything else is skipped and counted.
- **Transcript (one Spark call):** the run's single `transcript` artifact (none or several fail the run) goes to Spark with the market vocabulary, never the fact form (a form value must not pull a spoken "95" toward "92"). Strict `json_schema` output per market: `{ facts: [{ turnIndex, quote, key, otherKey, value, unit, basis, assertion }] }` with `key` an enum of the profile's fact keys plus `other`, `unit` an enum of the profile's units, `basis` an enum of `area_bases` plus `unspecified`, `assertion` `stated | opinion`. Model, effort, and `max_output_tokens` come from the step; the call goes through `ctx.ledger.meter` with `metaProviderOptions` (`store: false`).
- **Validation in code (`normalizeExtractedFacts`), never trusting the model:** the turn must exist; the quote must occur in that turn up to whitespace and case only, and the stored quote is the exact span of the turn's text (so `turn.text.includes(quote)` holds); `other` + `otherKey` becomes `other:<slug>`, and any key not chosen from the enum is filed under `other:` too, never promoted to a profile key; profile facts take the profile's unit (a different unit from the model drops the fact) and a type-valid value (only unambiguous repairs: enum case, a plain digit string, `yes`/`no`); areas take a listed basis or `unspecified` (a missing or unknown basis becomes `unspecified`), every other fact basis `null`; anything but an explicit `stated` is stored as `opinion`; exact repeats in one turn are dropped, the same quantity in two turns is kept twice. Dropped facts and their reasons (`unknown_turn`, `quote_mismatch`, `invalid_key`, `invalid_value`, `unit_mismatch`, `duplicate`) go into the report artifact.
- **Output:** a `fact_extraction` singleton artifact (`factExtractionReportSchema`: prompt version, transcript artifact ID, model settings, counts, rejected items with clipped model text) plus the candidate `facts` rows, and a `facts_extracted` event with counts only. A truncated answer (`max_output_tokens` reached) fails the run instead of retrying at the same cap.
- **Idempotency:** the report is a singleton per run and step (`artifacts_singleton_kind_key`), and the facts are inserted only when the report row is created, in the same `commit(tx)`. A repeated commit therefore keeps the first candidate set whole. A per-row `ON CONFLICT` would instead merge two different (non-deterministic) model answers into one set.
- **Reconciliation input:** candidates use the catalog's field names (`key`, `value`, `unit`, `basis`, `quote`, `startMs`, `endMs`, plus `assertion`), so P2-09 only assigns catalog IDs (`F.<field>`, `Tnn`, `Cnn`). The catalog schema was widened for this: input values may be booleans, `speaker` is any label or `null` (diarization yields `A`, not roles), and candidates may carry `assertion`; the P1-03 fixtures are unaffected.

**Integrity check (P1-07: GO, scoped; step P3-05).** Comparison: `apps/api/src/pipeline/integrity/compare.ts`; step: `check.ts` (model-facing core), `handler.ts` (registered in `worker.ts` as agent `integrity_checker`); contracts in `packages/shared/src/integrity.ts`; evidence, margins, and blind spots in [model-notes.md](./model-notes.md#p1-07--integrity-check-feasibility), step measurements in [model-notes.md](./model-notes.md#p3-05--integrity-check).

- `compareFixedElements(original, edit, { thresholds?, elements? }) → IntegrityVerdict` is pure (no I/O, no model calls). Each image is `{ width, height, segments: Record<label, { box }[]> }`, so `segmentImage` results fit directly. The verdict has `passed`, `aspectRatioChange`, image-level `failures` (`aspect_ratio_changed`), `failedClasses`, and per class: counts, `countDelta`, matches (IoU, containment, area ratio, accepting rule), `worstMatchedIoU`, unmatched instances with their best IoU, and `failures` (`count_changed`, `unmatched_original`, `unmatched_edit`). Invalid input throws `IntegrityInputError`.
- Settings come from the step (§7: `fixed_elements`, `min_iou`, `min_containment`, `min_area_ratio`, `max_aspect_ratio_change`, `edit_privacy_phrases`). v1 uses the P1-07 values (`DEFAULT_INTEGRITY_THRESHOLDS`, `DEFAULT_FIXED_ELEMENTS`): `minIoU` 0.75, `minContainment` 0.85, `minAreaRatio` 0.4, `maxAspectRatioChange` 0.03; `window` not occlusion-tolerant, `door` and `radiator` tolerant. On the six synthetic pairs, 5/5 harmless edits pass with at least 0.12 slack and the window-removal edit fails on its count; the five recorded P3-04 edits all pass (P3-05).
- It catches removed, added, and moved fixed elements; it does not see elements resized or restyled in place within tolerance, walls, floors, worktops, cabinets, or anything outside the segmented classes. Gate 2 (original next to staged image) remains the backstop.
- **Input:** the run's single `staged_images` manifest (none or several fail the run with `NonRetryableStepError` before any call) and, per `staged` entry, its `staged_image` artifact (same run, kind, material, and operation as the entry; the file's SHA-256 must equal `stored.sha256`) and the original, read and checked like staging does (`readOriginals`: ready, size, checksum, header, and the record's SHA-256 and dimensions). Any mismatch is a storage fault and fails the run. The retry's image model comes from the service's `stager` step (`stagingSettings`).
- **Per staged photo** (2 photos at once, at most 4 SAM calls in flight per photo; `checkStagedPhoto`): the original's fixed elements (3 calls) and the edit's fixed elements plus `edit_privacy_phrases` (4 calls) are segmented together; the original's result is reused for the retry, so a checked edit costs 4 calls and a photo 7 (11 with a retry). The attempt passes when the verdict passes and no privacy phrase has an instance (staged originals are privacy-`clear`, and a staged image has no masks the export could blur). A failed attempt re-runs the same declared operation once (`restageSameOperation` → `stagePhoto` with `stagingOperation(operation.id)`: same prompt, size, and tools-off body; metered) and checks the new image against the same original segmentation. Outcomes: `passed`, `passed_on_retry`, `fallback_original` (both failed, the retry edit failed, or the check could not run).
- **Errors:** photo-level SAM failures (`rejected_input`, `invalid_output`, `incomplete_response`, as in vision) and a SAM box outside its own image make the attempt `unchecked`, and the photo falls back to its original without a retry (fail-closed: an unchecked edit is never offered; a retry costs more than the check and would most likely be unchecked too). A photo-level retry-edit failure (`rejected_input`, `no_image`, `invalid_output`) is recorded as `edit_failed`. Everything else (429/5xx after the SDK's retries, timeouts, abort, budget) propagates to the engine's transient/non-retryable split; after the first such error no new photo starts and running calls are awaited. A step with nothing staged completes with an empty record and no calls.
- **Output (one commit):** each retry image as a `staged_image` artifact of the integrity step (same content schema as staging's, stored whatever its verdict so every verdict points at an image), then one `integrity_checks` artifact (`integrityChecksContentSchema`: segmentation model, the manifest's ID, the fixed elements, thresholds, and privacy phrases used, counts, and per staged photo in manifest order: `materialId`, `operationId`, the original's segmentation (boxes and scores per phrase, no masks; `null` if it failed), `attempts` (1–2; `checked` with the edit's segmentation, the full `IntegrityVerdict`, and the privacy counts; `unchecked` with `target` and reason; `edit_failed` with reason), `outcome`, and `finalStagedArtifactId`). The schema refuses an outcome or final image that does not follow from the last attempt. Plus an `integrity_checked` event with counts only. Step output IDs: the record, then the retry images. Retry files are written before the transaction and deleted if anything fails before or inside `commit`; a repeated commit keeps the stored record and deletes the new files.
- **For Gate 2 and the export (P3-08, P3-09):** the only staged image that may be shown for approval or exported for a photo is its `finalStagedArtifactId` in the run's `integrity_checks` record; photos with `fallback_original` offer no staged image. Every other `staged_image` artifact (failed first attempts under `staging`, failed retries under `integrity`) stays stored for audit and for showing next to its verdict, never for export. Gate 2 can draw the stored boxes of `original` and each attempt's `edit` over the two images.

**Vision inventory (P2-08).** Code: `apps/api/src/pipeline/vision/` (`handler.ts`, `inventory.ts`, `normalize.ts`, `selection.ts`, `regions.ts`, `downscale.ts`, `errors.ts`, `prompt.ts`, `schema.ts`), registered in `worker.ts`; contracts in `packages/shared/src/vision.ts`; measurements in [model-notes.md](./model-notes.md#p2-08--vision-inventory).

- **Input:** the project's `ready` photos uploaded before the run was created, in upload order. None, more than the service's `images.max`, a missing file, a checksum or header-size mismatch, or invalid metadata fail the run with `NonRetryableStepError` before any model call. The service minimum is enforced when a run is started (P4), not here.
- **Phase 1, per photo (all photos, at most 4 model calls in flight):** one Spark call (strict `json_schema`, model/effort/`max_output_tokens` from the step) on a copy downscaled to `classification_long_edge_px` (1024 in v1; smaller photos go byte for byte), returning subject (closed set `PHOTO_SUBJECTS`), furnishing (`empty | partly | furnished`, null for exteriors, balconies, terraces, gardens, views, plans, and documents), a one-sentence summary, quality (`good | acceptable | poor`) plus issues, a cover score 1–10, observations (`object` from the market's `evidence_objects` or `other` + slug, count, detail), and which privacy phrases are visible. In parallel, one SAM call per `privacy_phrases` entry (`person`, `license plate`) on the **stored** photo, always, uncapped.
- **Furnishing (prompt version 2, decided 2026-10-29):** how much movable furniture an interior room holds, so staging can furnish empty rooms only. Fixed installations never count (built-in wardrobes and cupboards, kitchen units and worktops, sanitary fittings, radiators, appliances, light fittings, curtains, blinds). `empty`: no movable furniture and nothing else standing on the floor; `partly`: some movable furniture or loose objects (a single chair, a bare mattress, boxes, tools) but the room is not set up for its use; `furnished`: the room's main furniture is in place. The prompt says to choose the more furnished value when unsure. Stored as `classification.furnishing` (`FurnishingState | null`): null means unknown, and is never read as `empty`.
- **Validation in code (`normalizeClassification`):** subject and quality must be in their sets (else the photo's classification fails); furnishing is set to null for the subjects in `FURNISHING_NOT_APPLICABLE_SUBJECTS` and for a value outside its set (recorded in `repairs` as `furnishing`; the photo still classifies, because furnishing only gates staging); cover score and counts are rounded and clamped (recorded in `repairs`); `other` names must be `snake_case` slugs (a slug naming a configured object becomes that object); zero counts, duplicates per photo, and observations beyond 15 are rejected and listed in the artifact.
- **Phase 2, evidence (`max_evidence_masks` per run):** only (photo, object) pairs that Spark observed and that have a SAM phrase are candidates, so no call is spent on objects Spark did not see. `selectEvidenceRequests` picks at most the cap, breadth first: one request per distinct object in market priority order (better-quality photos first) before a second photo of any object. Evidence masks are capped too: every answered request keeps its best-scoring mask, then the remaining budget goes in request order; boxes are kept for every instance.
- **Cover rank:** deterministic over classified photos: cover score, then quality, then fewer issues, then upload order (1 = best).
- **Privacy status per photo** (precedence top-down): `failed` (a privacy call failed: the photo is **not** privacy-checked), `review` (SAM found nothing for a phrase Spark reported visible), `masked` (regions found; their masks are stored), `clear`. Export (P3-09) may publish only `clear` and `masked` photos without a human decision, blurring the stored masks (boxes are in stored-photo pixels).
- **Errors:** a photo-level failure (unparseable or truncated Spark answer, malformed SAM output, a non-retryable 400/413/415/422) is stored on that photo (`classification.status: failed` or a failed privacy phrase / evidence request) and the step continues, because a step retry would fail the same way and re-pay every other photo. Everything else (429/5xx after SDK retries, timeouts, abort, budget, pricing) propagates to the engine's transient/non-retryable split; after the first such error no new call starts and in-flight calls are awaited. If every photo's classification, or every photo's privacy check, fails, the run fails (`NonRetryableStepError`). There is no in-step retry layer.
- **Output:** one `photo_inventory` artifact (`photoInventoryContentSchema`: settings, counts, evidence cap usage, and per photo the classification, privacy results with regions and masks, and observations with their evidence status, regions, and fact region) and one `photo_region` candidate fact per observation: key `other:<object>`, value = SAM's instance count when segmented, else Spark's count, `unit`/`basis` null, `assertion: stated`; region = union of the SAM boxes, else the whole photo; `maskArtifactId` = the inventory artifact when masks exist (the masks are those of the observation with the fact's key in the photo with the fact's `materialId`). An observation SAM was asked about and did not find (`not_found`) gets no fact. A `photos_inventoried` event carries counts only. **Inventories stored before prompt version 2** have no `furnishing`; the schema reads the absent field as null (unknown), so no migration is needed and staging never furnishes their rooms.
- **Idempotency:** `commit` inserts the artifact and facts only if the step has no `photo_inventory` yet. It runs inside the engine's completion transaction (run row locked, claim re-checked, at most one completed attempt per step), so this check is serialized; `photo_inventory` is not in the singleton index (no migration).
- **Reconciliation input (P2-09):** `photos[].room` = subject (furnishing is not sent), `summary`, observations → `Pnn.Rk` with label + detail; `supports` links an object to profile facts (e.g. `balcony → outdoor_space` in `international`, `energy_label → energy_label` in `nl`). Cross-photo aggregates (distinct bedrooms) are not produced here.

**Reconciliation (P2-09).** Code: `apps/api/src/pipeline/reconciliation/` (`handler.ts`, `catalog.ts`, `compare.ts`, `resolve.ts`, `call.ts`, `step-prompt.ts`, `schema.ts`), registered in `worker.ts`; contracts in `packages/shared/src/reconciliation.ts`; measurements in [model-notes.md](./model-notes.md#p2-09--reconciliation). The P1-03 prototype (`prompt.ts`, `score.ts`, its fixtures) is kept unchanged for its measurement test.

- **Input:** the run's `candidate` facts (form, transcript, photo), the single `transcript` artifact, and the single `photo_inventory` artifact (none of either is fine when no fact cites it; several, or a fact citing a transcript the run does not have, fail the run with `NonRetryableStepError`). `buildCatalog` assigns catalog IDs from content, never from database IDs or insertion order: form fields `F.<field>` in field order, transcript candidates `Cnn` in spoken order (turn, quote offset, then content), photo regions `Pnn.Rk` in inventory order with the fact key and per-photo count. The model sees `marketFacts` (key, type, unit, basis), the form, all turns, the **stated** candidates (opinions get an ID but are not sent), and the photos; never fact IDs, timestamps, or regions.
- **Market facts are decided by code** (`compareProfileFacts`, the basis rule): per profile key, facts on the profile's measure (its unit and, for areas, its basis) decide: one value is verified (`agreement` / `single_source`), several values are one conflict (`value_mismatch`). A fact on another measure is compared with the verified value only: stated without a basis and equal, it corroborates (`corroborating`); otherwise it is rejected as `different_basis` / `different_unit` with a **basis note** on the sheet, and never joins or decides a conflict. Numbers are compared exactly (same JSON type, `===`): no tolerance, because "92" and "92.5" are different claims. The planted walkthrough values (form 92 NEN 2580, turn 92 NEN 2580, turn "zo'n 95" unspecified) therefore give a verified 92 and a basis note for 95, not a conflict.
- **The model proposes, code verifies** (`resolveReconciliation`): Wonder (fallback Spark) returns `verifiedFacts { key, value, evidenceIds }`, `conflicts { key, kind, evidenceIds, explanation }`, `rejected { evidenceId, reason: opinion | out_of_scope | ambiguous, explanation }`. Unknown IDs are dropped and counted. A verified value must equal a cited form field's or candidate's value exactly under its key (the `other:` prefix may be omitted, nothing else); other citations must agree with it by the basis rule: an equal value supports, a different value on the same measure turns the group into a conflict, another measure gets a basis note, and a different text under a different key is dropped. Photos support presences, never measurements. The model cannot verify or reject a market fact, reject a form value or photo observation, or verify an opinion. Its conflicts on measurements must pass the basis rule; same-key conflicts on market facts are code's alone. Escalation is allowed, de-escalation is not: a valid model conflict pulls every entry it touches into Gate 1, and conflicts that share a fact are merged, so conflicts are disjoint. Form values and photo observations nothing grouped stand on their own (`single_source`); a transcript `other:` candidate the model did not account for validly is rejected as `not_reconciled`, never verified by default. Counters of what survived go into `diagnostics`.
- **Cross-photo aggregates are not derived.** The inventory has no room identity across photos (two photos of one bedroom would count as two), so a photo-derived room count would raise false conflicts at Gate 1. Photos are presence evidence: the prompt forbids totals from photos, and a photo can contradict a statement that something is absent or different, not a count or measurement.
- **Fallback:** the call goes through `ctx.ledger.meter` with model, effort, and `max_output_tokens` from the step. A primary failure the model is responsible for (an `APICallError`, retryable after the SDK's retries or not, a `RetryError`, the SDK's `TimeoutError`, or an unparseable/truncated answer) runs the definition's `fallback_model` at `fallback_reasoning_effort` once; budget, pricing, ledger, and abort errors never do. A billed primary failure (e.g. truncated) and the fallback are both ledger rows. The sheet records `modelRun { model, reasoningEffort, maxOutputTokens, fallbackFrom: { model, reasoningEffort, failure } | null }` (`failure` is a class such as `APICallError 503`, never an SDK message). A truncated fallback fails the run (`NonRetryableStepError`); other fallback errors go to the engine's retry. A run with only form candidates makes no call.
- **Output (one commit):** a `verified_fact_sheet` artifact (`verifiedFactSheetContentSchema`: prompt version, model run, counts, entries `V01…` with value/unit/basis, fact IDs, evidence IDs, source kinds, reason; basis notes; one outcome per candidate with status, reason, decider, entry/conflict ID, and the model's note for rejections; diagnostics), a `fact_conflicts` artifact (`factConflictsContentSchema`: the sheet's ID and conflicts `K01…` with key, kind, detectors, explanation, all fact IDs, and sides grouped by key + value + unit + basis), every candidate's status (`verified | conflicted | rejected`; there is no reason column, the reason is in the sheet), and a `facts_reconciled` event with counts, the model, and `fallbackUsed`.
- **Gate 1:** the step's commit returns `releaseGate: true` when there are no conflicts, so the engine releases `gate_after` and the run continues; with conflicts the run stops at `fact_conflicts`. Conflicts are disjoint, so one decision per conflicted fact (`decisions.target_kind = 'fact'`) resolves exactly one conflict; a conflict is decided when each of its `factIds` has a decision, and the run resumes when all are (Gate 1 API below). The sheet is the immutable snapshot before Gate 1. After the gate, the `verified` facts are authoritative: the Gate 1 API applies every decision to the facts when it releases the gate, so creative (P3-01) builds from `verified` facts only and no post-gate sheet is written; the decisions remain the audit record.
- **Idempotency:** `commit` writes only if the step has no `verified_fact_sheet` yet (inside the engine's completion transaction, like vision); a repeated commit returns the stored artifacts and the same gate decision. Status updates must touch every read fact, or the commit fails.

**Gate 1 API (P2-10).** Code: `apps/api/src/gates/` (`fact-conflicts.ts` service, `routes.ts`), mounted in `createApp` at `/api/runs` behind `requireUser`; contracts in `packages/shared/src/gates.ts`. Responses are `Cache-Control: no-store`; errors use `apiErrorSchema` (§14).

- **`GET /api/runs/:runId/gates/fact-conflicts`** → 200 `factConflictsGateResponseSchema`: `{ runId, runStatus, state, factSheetArtifactId, conflictsArtifactId, conflictCount, openCount, conflicts[] }`. `state` is `not_reached` (no `fact_conflicts` artifact yet), `open` (run `awaiting_gate` at `fact_conflicts`; decisions accepted), `released` (the reconciliation step's `gate_released_at` is set: by the last decision, or by the step itself when there was nothing to decide), or `suspended` (gate held but the run failed there; `resumeRun` reopens it with the decisions made so far). Each conflict carries the artifact's `id`, `key`, `kind`, `detectedBy`, `explanation`, its `sides` (value, unit, basis, evidence IDs, source kinds) with each side's `facts` (`id`, `key`, `value`, `unit`, `basis`, `status`, `assertion`, and `source`, the full provenance: form field, transcript artifact + turn + ms + quote, or photo material + region + mask artifact), and its `decision` (null while open). `openCount` is 0 once released.
- **`PUT /api/runs/:runId/gates/fact-conflicts/conflicts/:conflictId/decision`** with one of `{ choice: 'accept', factId }`, `{ choice: 'edit', value, key?, unit?, basis? }`, `{ choice: 'reject' }` (strict objects; edited text is trimmed, 1–300 characters; values are exact scalars) → 200 `factConflictDecisionResponseSchema` (the GET body plus `resumed`). Errors: 400 `validation_failed` (body or path, or an edited value that does not fit: an `edit` key outside the conflict's keys, a value invalid for a market fact's type, a unit or basis other than the profile's), 400 `fact_not_in_conflict`, 401 `unauthenticated`, 403 `forbidden_origin`, 404 `not_found` (unknown run, another user's run — never 403 — or unknown conflict), 409 `gate_not_open` (the run is not awaiting this gate: not reached, released, or failed), 415 `unsupported_media_type`.
- **Decisions** (one row per conflicted fact, `gate = fact_conflicts`, written together by `upsertDecisions`): `accept` → the side containing `factId` gets `accept`, every other fact `reject`; `edit` → every fact gets `edit` with `edited_value = { key, value, unit, basis }` (for a market-profile key the profile fixes unit and basis; `other:` keys take the given unit/basis or null); `reject` → every fact `reject`. `remove` is not used at Gate 1. A conflict's decision is derived back from its rows only when they have exactly one of these shapes; anything else reads as open and is overwritten by the next decision.
- **Changes and idempotency:** while the gate is open a decision can be replaced (rows are upserted; `decided_at` and `decided_by` move with the change). Repeating the same decision writes nothing and keeps `decided_at`. After the gate is released every decision returns 409.
- **Fact status rules, applied once when the gate is released** (until then the facts stay `conflicted`, so changing a decision never rewrites facts): accept → the accepted side's facts `verified`, all other facts of the conflict `rejected`; edit → every fact of the conflict `rejected`, plus a new fact (`step_id = 'gate:fact_conflicts'`, `source_kind = gate_decision`, `source_ref = { gate, conflictsArtifactId, conflictId }`, `status = verified`, `assertion = stated`) carrying the operator's value; reject → every fact of the conflict `rejected`, nothing on the sheet. An edited value is therefore never attributed to a form field, turn, or photo that did not state it, and the evidence inspector shows it as the operator's decision. Accepting a side with an opinion is refused (reconciliation never puts opinions into conflicts; `facts_opinion_never_verified` backs this up).
- **Resume:** each PUT runs in one transaction that first checks ownership, then locks the run row (`lockRun`, the engine's lock order) and checks the gate. The request whose decision leaves no conflict open applies the fact updates, appends `gate_decided` (counts only, §9), and calls `resumeAfterGate(runId, { gate: 'fact_conflicts', tx })`, so the gate release, `awaiting_gate → running`, and the next step's pg-boss job commit with the last decision or not at all. Concurrent decisions serialize on the lock: of two "last" decisions on different conflicts exactly one resumes; a repeat of the last decision racing it gets 409. Auto-resume was chosen over a separate resume endpoint: deciding the last conflict is the operator's signal, and one request cannot leave a fully decided gate waiting.
- **API process:** the API now starts its own pg-boss instance (send only: `supervise` and `schedule` off; workers and maintenance stay in the worker) and a run engine without handlers, creates the queues at boot, and on shutdown closes the HTTP server, then pg-boss, then the pool.

**Creative copy (P3-01).** Code: `apps/api/src/pipeline/creative/` (`handler.ts`, `catalog.ts`, `generate.ts`, `check.ts`, `language.ts`, `prompt.ts`, `schema.ts`), registered in `worker.ts` under the `creative` agent; contracts in `packages/shared/src/copy.ts`; measurements in [model-notes.md](./model-notes.md#p3-01--creative-copy). Copy only: staging is its own step (P3-04).

- **Input (`loadCopySources`):** the run's `verified` facts after Gate 1, every source kind including `gate_decision` facts from an `edit` (the pre-gate `verified_fact_sheet` is not read); the photo inventory for context only (the distinct room subjects in cover-rank order and the cover's subject, closed-set values only, so no model-written summary reaches the prompt); the project's office profile `tone` (null → "warm, clear, and factual"); the run's `output_language`, which must be one of the market's `output_languages` (else `NonRetryableStepError`, no call); and the market profile (currency, units, area bases, fact labels, `flagged_phrasing`). No verified fact also fails the run before any call.

A photo fact's stored value is an instance count in one photo, never a property total, so the model never sees it. Order: market facts in profile order, then `other:` keys in code-point order, then value, unit, basis; database IDs and insertion order never matter, so the request hash is stable for replay. Code maps each cited ID back to every stored fact behind it.
- **Opinions** (`assertion = opinion`) are never sent and never citable, not even as attributed atmosphere text: they are never verified, the database forbids verified opinions, and the catalog refuses them. Sales atmosphere comes from the tone, not from unverifiable statements.
- **Output:** two variants. `portal`: the portal description, 2–4 paragraphs, 120–220 words. `social`: one caption for Instagram and Facebook, 25–60 words, no hashtags or emojis. Each is an ordered list of segments `{ text, factIds }` (one sentence or clause each; paragraphs for the portal). One strict `json_schema` call (name `listing_copy`) with model, effort, `max_output_tokens`, and an optional fallback from the `creative` step; `factIds` is an enum of the request's catalog IDs, so strict mode already stops invented IDs. The prompt (`buildCopySystemPrompt`) forbids superlatives and promises in every market and adds exclusionary phrasing when the market lists it; requires digits exactly as the cited value (no rounding, conversion, ranges, thousands separators, or spelled-out numbers) and no number that is not a cited fact's value; forbids counts or measurements from presences; forbids the street and house number (the portal shows the address in its own fields; the town may be named); and requires the portal to state every market fact present.
- **Uncited text:** the prompt forbids segments without a fact (connecting words belong to the segment they introduce; no greetings, calls to action, contact details, or sign-offs: export adds the office's contact block). Code then repairs what slips through, deterministically: an uncited segment is joined to the next cited segment of its paragraph (or the previous one at the paragraph's end), so it is validated and verified together with the claim it leads into; a paragraph that cites nothing at all is dropped. Repairs are counted in the artifact and the event. So every stored segment cites at least one fact, and P3-02's "empty `fact_ids` → reject" never sees connective text.
- **Code checks before anything is stored (`checkCopyOutput`), not the claim validator:** the answer must parse against the schema (the SDK); every cited ID must be in the catalog; each variant must keep at least one cited segment; each variant must be in the output language (`checkLanguage`: function words unique to `en` or `nl`; `match`, `inconclusive` on too little evidence, `unchecked` for languages without a word list, a clear other language fails). Text is whitespace-normalized and trimmed. Numbers against the cited facts are the claim validator's job (P3-02, below), which runs after this check and never discards copy.
- **Errors (like reconciliation):** a truncated answer → `NonRetryableStepError` (a retry at the same cap pays for the same truncation); an unparseable answer or a failed check (`CopyOutputError`: `unknown_fact_id`, `empty_variant`, `wrong_language`, message with counts only) is a model failure: the step's `fallback_model` runs once if defined (none in `listing-launch` v1), otherwise the engine retries the step once. Budget, pricing, and abort errors never fall back.
- **Output (one commit):** a `listing_copy` artifact (`listingCopyContentSchema`: prompt version, model run, output language, tone, `revision` 0, `previousArtifactId` null, the catalog mapping `VFnn → fact IDs`, the variants with segments `{ index, paragraph, text, catalogIds, factIds }`, language checks, repairs, counts, and the claim validator's report `validation`), one `claims` row per segment (`segment_index = index`, the stored fact IDs, `validator_result` and that segment's findings in `validator_details`; verifier columns empty), and a `copy_generated` event with counts only (including `validatorResult`, `validatorFailedSegmentCount`, `validatorFindingCount`). The `claims` table fits as is: one row per segment of one artifact, with the variant and paragraph in the artifact; no migration.
- **Idempotency:** `commit` writes only if the step has no `listing_copy` yet (inside the engine's completion transaction); a repeated commit returns the stored artifact.
- **Revision loop (P3-06):** the engine completes a step once, so verification does not re-run `creative`. It calls the same functions: `loadCopySources(db, run, market)` → `buildCopyInput({ ...sources, revision: { draft: toCopyDraft(previous), flags } })` → `buildCopyRequests(creativeStep, market, input)` (model settings stay those of the `creative` step) → `generateListingCopy(deps, requests, catalog, language)` → `buildListingCopyContent({ ..., facts: sources.facts, revision: n, previousArtifactId })` (validates the revision) → `storeListingCopy(tx, { runId, stepId: 'verification', content })` in the verification step's commit (Verification below). A flag is `{ variant, segment, problem }` (0-based position within the variant). The system prompt already carries the revision rule, so a revision needs no prompt change. Catalog IDs are content-derived and stay valid while the verified facts are unchanged.

**Claim validator (P3-02).** Code: `apps/api/src/pipeline/claims/` (`validator.ts`, `numbers.ts`); report contract in `packages/shared/src/claims.ts`. A pure function, independent of the step that wrote the segments: `validateClaims({ language, segments: [{ variant, segmentIndex, text, factIds }], facts })` → `ClaimValidationReport`. `facts` are stored fact rows (`id, key, value, unit, status, assertion, source.kind`; a `Fact` satisfies it), either all of the run's or only the verified ones. Rules version 1 (`CLAIM_VALIDATOR_RULES_VERSION`), languages `en` and `nl` (`isClaimLanguage`); `buildCopyInput` refuses any other output language before a call, because copy whose numbers cannot be checked is not worth paying for.

- **Citations:** no fact IDs → `missing_fact_ids`; an ID not among `facts` → `unknown_fact_id`; a fact that is not `verified` → `unverified_fact`; an opinion → `opinion_cited`. Invalid citations never support a number. Gate 1 `gate_decision` facts are verified, stated facts like any other.
- **Number claims** (`readNumbers`), read in the segment's language: digits with that language's separators only (`en` `1,250.5`, `nl` `1.250,5`; the other language's form, a stray leading separator, glued letters such as `165k`, `1980s`, `2x`, or a scale word such as `million`/`miljoen` → `unreadable_number`; English `1.250` is 1.25); a currency sign or `EUR` before, the Dutch `,-` after; ordinal suffixes (`1st`, `2e`, `2de`, `8ste`); number words 0–99 and ordinal words 1–20 in `en`/`nl` (plus `pair`, `dozen`, `dozijn`, `anderhalf`); dates and times (`12-03-2027`, `10:30`, `10.30 uur`) as one token. Years are ordinary numbers.
- **Matching:** a number passes when a valid cited fact states exactly that value (`===` after parsing; no rounding, so 95 ≠ 94.6). Number facts state their value; text facts state the numbers in their text (read with the same rules); booleans state none; dates and times must appear verbatim in a cited text fact. Otherwise `number_not_in_facts`.
- **Units:** canonical aliases (`m2`/`m²`/`sq m`/`vierkante meter`, `m3`, `m`, `km`, `cm`, `kWh`, `kWp`, `EUR`/`€`/`euro`, `%`/`procent`, `year`/`jaar`, `minute`/`minuten`, `hour`/`uur`). A unit in the text must equal the matching fact's canonical unit, or be absent ("92" for 92 m² passes); otherwise `unit_mismatch`. A fact without a unit takes one from its key's last word when that is a unit alias (`other:station_cycling_time_minutes` → minute), else it has none and any written unit mismatches ("3 m²" against a room count). Unknown fact units only match themselves. Area basis is not checked here (the verifier judges "living space" against the basis).
- **Photo facts** (`source_kind = photo_region`) are presence evidence only: their stored value is a per-photo count, so they never support a number, even an equal one. An unmatched number in a segment that cites a photo fact is `number_from_photo`.
- **Approximation and ranges:** approximate wording directly before a number (`about`, `approx.`, `around`, `roughly`, `nearly`, `almost`, `some`, `more/less than`, `at least/most`, `up to`, `±`, `~`; `ca.`, `circa`, `zo'n`, `ongeveer`, `bijna`, `ruim`, `rond (de)`, `pakweg`, `krap`, `dik`, `meer/minder dan`, `minimaal`, `maximaal`, ...) or after it (`95+`, `90-ish`, `or so`, `of zo`) is `approximate_number`, even when the number matches: softening an exact fact misleads. Two numbers joined by `-`, `–`, `to`, `or`, `tot`, `t/m`, `à`, `of`, or "between/tussen X and/en Y" are a `number_range`; each end is also checked.
- **Number words:** mapped and validated, not rejected outright: "drie kamers" with a cited 3 is true, and the prompt already asks for digits. `one` and `een` are not read (pronoun and article; the stressed `één` is). Ordinal words are claims ("first floor" needs a cited 1; the UK/US floor ambiguity is the verifier's), so an enumerating "the second bedroom" is flagged unless a cited fact is 2: a revision fixes it cheaply, a missed floor claim would mislead. Vague quantities ("a few", "several", "both") carry no number and are the verifier's.
- **Not claims (explicit allowlist):** standard names `NEN 2580` / `NEN-2580` / `NEN 2580:2007` / `NEN-EN 13829`, and the house type `2-onder-1-kap`. Digits glued to a preceding letter (`m2`, `CO2`, `A0`, `HR107`) are units or names; energy label classes contain no digits.
- **Report:** `{ rulesVersion, language, result: pass | fail, counts: { segments, failedSegments, numbers, findings }, findings[] }`; a finding is `{ variant, segmentIndex, code, token, factId, detail }`, in segment then text order, one per distinct (code, token, fact). `token` is the offending span capped at 60 characters (never the segment), `factId` the cited ID for citation codes and unit mismatches, `detail` one English sentence from templates (usable as a revision flag's `problem` and in Gate 2). Every finding rejects its segment. Findings quote copy, so they share its personal-data scope: artifact and `claims` only, never events or logs.
- **Integration and failure policy:** `buildListingCopyContent` runs the validator (`validateCopy`: variant = kind, `segmentIndex` = `segment.index`) against the verified facts the catalog was built from (`CopySources.facts`), so the first draft and every revision carry a report. A failing segment is **kept, not dropped and not retried**: the step completes, `storeListingCopy` marks its claim `fail` with its findings, verification (P3-06) turns the findings into revision flags (`{ variant, segment: position in variant, problem: detail }`) for up to two loops, and what remains reaches Gate 2 as flags. Failing the step would pay for a full regeneration that the revision loop does better with targeted flags; dropping segments would silently change the copy (and could drop a required market fact).
- **Consumers:** P3-03 calls `validateClaims` with its Q&A answer segments (`validateQa`: `variant: 'qa'`, `segmentIndex` = the answer segment's index) and the verified facts; P3-06 reads `content.validation` / `claims.validator_details` and re-validates each revision through `buildListingCopyContent` / `buildQaCardsContent`; Gate 2 (P3-08) shows `detail` per claim and validates edited copy and Q&A answers.

**Buyer Q&A cards (P3-03).** Code: `apps/api/src/pipeline/qa/` (`handler.ts`, `generate.ts`, `check.ts`, `prompt.ts`, `schema.ts`), registered in `createStepHandlers` as agent `qa_writer`; contracts in `packages/shared/src/qa.ts`; measurements in [model-notes.md](./model-notes.md#p3-03--buyer-qa-cards). The step sits after `creative` and before `staging` (Spark 1.3 `low`, `max_output_tokens` 8,000, no fallback in `listing-launch` v1).

- **Input:** exactly the copy's sources (`loadCopySources`: verified facts after Gate 1, the content-derived catalog `VF01…`, office tone, output language, market profile) without the photo context, which Q&A does not need. Same refusals before any call: no verified fact, an output language the market does not offer, or one the claim validator has no number rules for.
- **Call:** one strict `json_schema` call (name `qa_cards`) with model, effort, cap, and fallback from the `qa_writer` step; `factIds` is an enum of the request's catalog IDs. Output `{ cards: [{ question, answer: [{ text, factIds }] }] }`. The prompt (`buildQaSystemPrompt`, `QA_PROMPT_VERSION` 1): 4–8 cards, fewer only when the facts cannot answer four distinct questions; questions a buyer asks before a viewing (size and layout, rooms, energy label and heating, construction year, costs, outdoor space, parking, storage, surroundings), one topic per card; ask only questions the facts answer and answer only from the facts, so **no "unknown" answers and no referrals** ("contact the agent", "ask at the viewing": the pack's footer carries the contact block, and a referral cites nothing); answers of 1–3 segments that each cite at least one fact; the copy's numbers rule, presence rule, translation rule, and street ban; the copy's phrasing rules (`phrasingRule`: superlatives and promises always, plus the market's `flagged_phrasing`) **in questions and answers**; never ask whom the property suits.
- **Questions are not claims** (decided here): they cite nothing and get no `claims` row, so the claim validator does not run on them. They are still published, so code checks them (`questionProblem`): whitespace-normalized, 1–200 characters, ending with `?`, and **no number at all** (`readNumbers` in the output language: digits, number words, ordinals, plus an explicit list of quantity words it does not read: `one`, `single`, `both`, `double`, `twin`, `triple`, `once`, `twice`, decade words such as `sixties`; `één`, `enkel`, `beide`, `dubbel…`, `driedubbel…`, `tweemaal`, `jaren zestig`), because nothing could verify a number in a question; a tag question (`…, doesn't it?`, `…, toch?`) presumes its statement and is invalid. Energy classes (`A+++`) and vague quantities are left to the verifier. The verifier reads each question with its answers and applies the phrasing rubric to both (below).
- **Code checks (`checkQaOutput`) and repairs:** unknown catalog IDs → `QaOutputError unknown_fact_id`; empty answer segments are dropped; an uncited answer segment is joined to the card's next (or previous) cited one, as in copy; a card is **dropped whole** when no answer segment cites a fact (`uncited`), its question is invalid (`invalidQuestion`) or holds a number (`numberInQuestion`), it repeats an earlier question case-insensitively (`duplicateQuestion`), or it comes after the 8th kept card (`overLimit`). Dropping is safe for Q&A (unlike copy) because a card is self-contained and no card is required. An answer segment over 2,000 characters → `QaOutputError segment_too_long` (a model failure, not a schema error). No usable card → `QaOutputError no_cards`; a clear other language over questions and answers → `wrong_language`. A `QaOutputError` or an unparseable answer falls back once if the step defines a fallback, otherwise the engine retries the step once; a truncated answer → `NonRetryableStepError` (a retry at the same cap pays for the same truncation); budget, pricing, and abort never fall back.
- **Validator-failure policy (mirrors copy):** after the structural check, `buildQaCardsContent` runs the claim validator on the answer segments against the verified facts. A failing segment is **kept, not dropped and not retried**: its claim is stored `fail` with its findings, verification turns the findings into Q&A revision flags for up to `max_revision_loops` loops, and what remains reaches Gate 2. Failing the step would pay for a full regeneration that a targeted revision does better, and dropping silently would hide the defect from the audit; the recorded cards so far passed with zero findings.
- **Output (one commit):** a `qa_cards` artifact (`qaCardsContentSchema`: prompt version, model run, output language, tone, `revision` 0, `previousArtifactId` null, the catalog mapping, the language check, cards `{ card, question, segments: [{ index, text, catalogIds, factIds }] }` with segment indexes running across the cards, repairs with the dropped cards by reason, counts, and the validator report `validation`), one `claims` row per answer segment (`segment_index = index`, validator result and findings; verifier columns empty), and a `qa_cards_generated` event with counts only (`storeQaCards`). Idempotent like creative (a repeated commit keeps the stored cards). No migration: `claims` already fits, artifact kinds and event types are open text sets.
- **Revision (`toQaDraft` → `buildQaInput({ ...sources, revision: { draft, flags } })` → `buildQaRequests(qaStep, …)` → `generateQaCards` → `buildQaCardsContent({ revision: n, previousArtifactId })` → `storeQaCards(tx, { stepId: 'verification' })`):** a flag is `{ card, segment, problem }` (card position and position in its answer); the system prompt carries the revision rule (fix the flagged cards by rewording the question or answer, citing what is needed, or dropping the card; keep the others). Verification calls it (below).

**Staging (P3-04).** Code: `apps/api/src/pipeline/staging/` (`handler.ts`, `selection.ts`, `operations.ts`, `stage.ts`, `encode.ts`), registered in `worker.ts` as agent `stager`; contracts in `packages/shared/src/staging.ts`; measurements in [model-notes.md](./model-notes.md#p3-04--staging-variants).

- **Why its own step:** staging was part of step 5 (`creative.image_model`). Verification's revision loops (P3-06) regenerate copy only and must not re-run or re-bill image edits, and a staging failure must not re-bill copy. The step sits after `qa_cards` and before `integrity`; `image_model` moved from `creative` to it (`listing-launch` v1 edited in place, before any run existed).
- **Input:** the run's single `photo_inventory` artifact (none or several fail the run with `NonRetryableStepError` before any call) and, for the selected photos only, the stored originals, read and checked like vision does (size, checksum, header) and additionally against the inventory's SHA-256 and dimensions: a staged image is always linked to exactly the bytes the privacy check saw.
- **Selection (`planStaging`, deterministic):** per photo, in order: privacy must be `clear` (`review` and `failed` are never sent to Muse Image; `masked` is skipped in v1 because the original's masks do not fit a re-rendered frame, so the export could not blur a staged copy reliably); the classification must exist and quality must not be `poor`; the operation is `declutter` for an interior subject with the `cluttered` or `personal_items` issue, otherwise `furnish_<room>` for living room, dining room, bedroom, or study, otherwise none (`not_stageable`; kitchens and bathrooms without clutter, hallways, exteriors, plans); the operation's kind must be enabled (`operation_not_enabled`); a furnish operation needs a room vision judged `empty`: `partly` and `furnished` rooms are skipped as `room_not_empty` and rooms without a furnishing state as `furnishing_unknown`, never given another operation (a live run on a real photo set furnished two already-furnished rooms, and Muse Image swapped the existing sofa, rug, and dining set). Then by cover rank (best first): at most one furnished photo per subject (two independently furnished views of one room would show different furniture; there is no room identity across photos) and at most `max_staged_images` edits. Every inventoried photo gets one outcome: `staged`, `failed` (reason), or `skipped` (`classification_failed`, `privacy_review`, `privacy_failed`, `privacy_masked`, `poor_quality`, `not_stageable`, `operation_not_enabled`, `room_not_empty`, `furnishing_unknown`, `subject_already_furnished`, `cap_reached`).
- **Declared operations (`operations.ts`, `STAGING_PROMPT_VERSION`):** a fixed catalog (`furnish_living_room`, `furnish_dining_room`, `furnish_bedroom`, `furnish_study`, `declutter`), kinds `furnish | declutter` (the P1-07 scope). No model writes operation text. The prompt wraps the operation in fixed preservation instructions (P1-06's wording plus the P1-07 false-rejection risks: nothing in front of windows or doors; no mirrors, pictures, screens, curtains, wardrobes, cabinets, or tall furniture).
- **Enabled kinds (`operation_kinds`, decided 2026-10-29):** v1 allows `furnish` only. A photo whose fitting operation is of a disabled kind is skipped as `operation_not_enabled`, never given another operation, so a cluttered room is not furnished around its clutter. `declutter` stays in the catalog but is off: the live P3-04 edit of a cluttered kitchen redrew the worktop and base cabinets the clutter hid, and the integrity check does not cover those surfaces, so only a reviewer at Gate 2 would see it. The `staged_images` manifest records the enabled kinds.
- **Request:** one `editMetaImageToolsOff` call per photo (§4), at most 3 in flight, metered by `ctx.ledger.meter`; `size` is the original's own `WxH` (Meta reads it as an aspect ratio: 1024×682 came back 1920×1280, a 0.10% aspect change against the integrity check's 3%); `output_format: jpeg`; `n: 1`.
- **Stored file (`encodeStagedImage`):** re-encoded like an upload (fit 2048 px, sRGB, JPEG q85 mozjpeg, no input metadata, so the model's XMP is dropped), plus one XMP packet of our own with IPTC `DigitalSourceType = compositeWithTrainedAlgorithmicMedia` (machine-readable AI-edit disclosure; the visible label is the primary one). Key `projects/<projectId>/runs/<runId>/artifacts/<uuid>.jpg` (`newRunArtifactStorageKey`). Files are written before the completion transaction and deleted again if anything fails before or inside `commit`.
- **Output (one commit):** one `staged_image` artifact per staged photo, with the JPEG as the artifact's file and `stagedImageContentSchema` as content: `original { materialId, sha256, width, height }`, `operation { id, kind, text }`, the full `prompt`, `model`, `requestedSize`, `toolsDisabled: true`, `modelOutput { format, width, height }`, `stored { mimeType, width, height, sizeBytes, sha256 }`, `aspectRatioChange`, `disclosure { label: "Virtually staged", visibleLabelRequired: true }`. Plus one `staged_images` artifact (`stagedImagesContentSchema`: prompt version, model, cap, the inventory artifact ID, counts, and the per-photo outcomes with `stagedArtifactId`) and an `images_staged` event with counts only. Step output IDs: the manifest, then the staged images.
- **Errors:** a photo-level failure (400/413/415/422 → `rejected_input`; 2xx without an image → `no_image`, unbilled; undecodable bytes or another response shape → `invalid_output`) is recorded in the manifest and the step goes on. Everything else (429/5xx after the SDK's retries, timeouts, abort, budget) propagates to the engine's transient/non-retryable split; after the first such error no new edit starts. A step whose edits all fail still completes (staging is optional; the pack works with originals), with the failures in the manifest and the event. There is no in-step retry: the integrity retry belongs to P3-05.
- **Idempotency:** `commit` writes only if the step has no `staged_images` yet (inside the engine's completion transaction, like vision); a repeated commit keeps the stored set and deletes the new execution's files.
- **For the integrity check (P3-05):** read the step's `staged_images` (`stepId` of the `stager` step) and, per `staged` entry, the `staged_image` artifact: its file is the edit, `original.materialId` + `original.sha256` identify the original (stored-photo pixels, the same frame as the inventory's boxes). Segment each original once and reuse it for the retry. A retry re-issues the same request with `stagePhoto(deps, settings, photo, stagingOperation(content.operation.id))` from `stage.ts` (same prompt, size, and tools-off transport) and stores a new `staged_image` under the integrity step. The staged image has **no privacy masks** (only `clear` originals are staged, but the model could still draw a person or a portrait); P3-05 segments `person` on every checked edit and fails it on any instance ($0.0025 per image).
- **For Gate 2 and the export (P3-08, P3-09, P3-07):** Gate 2 decides each `staged_image` artifact that the integrity check names as final (`finalStagedArtifactId`, see Integrity check above; `decisions.target_kind = 'artifact'`) next to its original. The export and the checklist rule `staged_images_labeled` show `disclosure.label` with every staged image wherever it appears, and keep the original available; the stored XMP marker should survive the export's re-encode.

**Verification (P3-06).** Code: `apps/api/src/pipeline/verification/` (`handler.ts`, `rubric.ts`, `audit.ts`, `call.ts`, `loop.ts`, `step-prompt.ts`, `step-schema.ts`), registered in `worker.ts` as agent `verifier`; contracts in `packages/shared/src/claim-audit.ts`; measurements in [model-notes.md](./model-notes.md#p3-06--verification). The P1-03 sizing prototype (`prompt.ts`, `schema.ts`, its fixture) is kept unchanged for its measurement test.

- **Input:** the creative step's single `listing_copy` (the service's one `creative` step; none or several fail the run with `NonRetryableStepError` before any call), the Q&A step's single `qa_cards` when the service has a `qa_writer` step (at most one such step; none means roadmap cut level 1 and verification runs on copy alone; a Q&A step without exactly one `qa_cards` fails the run), the copy sources from `loadCopySources` (verified facts, photo rooms, tone, output language), and the market profile. Each draft's catalog must equal the catalog rebuilt from the current verified facts (otherwise its IDs would point at other facts) and its language must be the run's; any mismatch fails the run without a call.
- **Rubric (`buildVerificationRubric`, from the profile, never per market in code):** `claim_support` (every statement justified by the cited facts read literally: no added feature, condition, or comparison; no strengthened or reinterpreted fact; no count or size from a presence; no legal or commercial status words no fact states, such as "included", "freehold", "own land"; a false value supports only its plain negation); then the phrasing categories the copy prompt also forbids (`copyPhrasingCategories`: `unverifiable_superlative` and `investment_promise` always, plus the profile's `flagged_phrasing`, so `exclusionary` in both v1 profiles); then `area_basis`, built from the profile's area facts and basis labels (an area presented as living or plot area must cite that fact; any other area must say what it measures and never be added into it), omitted when the profile has no area facts. The categories are the closed set `CLAIM_AUDIT_CATEGORIES`; the rubric texts are stored in the audit.
- **Verifier call:** Wonder through the AI SDK, strict `json_schema` (name `claim_audit`), model, effort, `max_output_tokens`, and fallback from the `verifier` step (`muse-wonder-1.0` `low`, 12,000; fallback Spark `medium`). The user message carries the language, the market's units and bases, the rubric, the catalog facts the draft and cards cite (same shape as the copy input, presences included), and every segment as `{ id, paragraph, text, factIds, audit }` with IDs `P01…` / `S01…` / `Q01…` (variant initial + position). **Q&A in the same call (P3-03):** the cards' answer segments are a third text, `{ variant: 'qa', questions, segments }`, where `questions` lists the questions by card and a Q&A segment's `paragraph` is its card; one call instead of two saves the ~3k-token rubric and facts prefix. With Q&A the system prompt (`verificationSystemPrompt(true)`, `VERIFICATION_PROMPT_VERSION` 2) names the Q&A text and adds one paragraph: read each audited answer with its question, apply the phrasing rules to both, and flag a question that breaks a rule or presumes an unstated fact **on the first segment of its card**. Without Q&A the request is byte-identical to P3-06's (no `questions` key, the original prompt), so the P3-06 recordings still replay. The answer is **flags only**, `{ segment, category, problem, suggestion | null }`: a clean segment costs no answer tokens (P1-03's per-segment audits made the answer the main cost). `segment` is an enum of the segments marked `audit: true` and `category` an enum of the rubric's categories, so strict mode already refuses invented segments and rules.
- **Code checks every flag (`checkVerifierFlags`):** the segment must exist and be marked for audit, the category must be in the rubric, the problem must be non-empty after whitespace normalization (clipped at 500 characters, suggestions at 2,000; an empty suggestion becomes null), and repeats (same segment, category, problem) are dropped. Refused flags are counted per reason in the pass (`dropped`), never stored as flags. Flags carry no fact IDs, so there are none to forge.
- **Validator findings are hard flags:** each finding of the draft's `validation` (P3-02) becomes a `claim_support` flag with `source: validator`, its `code`, and its `detail` as the problem, addressed by position within its variant (`segmentIndex` is the global index). They are recomputed for every draft by `buildListingCopyContent` and never carried.
- **Loop (`runRevisionLoop`, `verifyCopy`):** audit the draft (and the cards); while there are flags (validator plus verifier) and fewer than `max_revision_loops` revisions were made, revise and audit again; stop at the first clean pass. **Each loop revises only what is flagged:** copy flags go to the copy revision below, `qa` flags to P3-03's Q&A revision (`toQaRevisionFlags` → card and answer position, suggestion appended), copy first; an unflagged draft stays as it is, its segments keep their verdicts, and it is stored once. A revision is numbered by the loop that wrote it (`revision: n`), so a draft revised only in loop 2 has revisions 0 and 2. The same loop limit, stop reasons, and budget/failure rules cover both: a Q&A revision failure (`QaOutputError`, truncation, an error response) also ends the loop as `revision_failed`. A revision is the P3-01 path with the `creative` step's own settings: `buildCopyInput({ ...sources, revision: { draft: toCopyDraft(previous), flags } })` → `buildCopyRequests(creativeStep, …)` → `generateListingCopy` → `buildListingCopyContent({ revision: n, previousArtifactId })`. Revision flags are `{ variant, segment, problem }` with the verifier's suggestion appended ("… Suggested rewrite: …", capped at 500), one per distinct problem. Stop reasons: `clean`, `loop_limit`, `budget`, or `revision_failed`.
- **Re-verification of changed segments only:** a segment whose variant, text, and citations equal one already audited in this step keeps that verdict (`carried`, including its flags: an unfixed flag stays flagged) and is sent as context with `audit: false`; only new or changed segments are audited. When nothing changed, no call is made (`modelRun: null`). Regeneration stays whole-draft: P3-01's interface returns a complete draft and its prompt already tells Spark to keep unflagged segments, which it did in every recording (1–5 segments changed). Measured: a revision costs ~$0.02 and its partial re-audit ~$0.021, against $0.026 for a full clean pass, because the ~3.2k input tokens dominate a Wonder `low` audit; the saving is ~20% per re-audit, the main gain is that unchanged text cannot flip verdict between passes.
- **Errors:** the verifier follows reconciliation's fallback policy (a model failure → the fallback once; budget, pricing, abort never; a truncated answer → `NonRetryableStepError`). A revision uses the `creative` step's fallback, if any. **Budget and failures inside a loop (decided 2026-10-29):** the first audit must complete (a budget error or model failure there fails the run as elsewhere). Inside a later loop, a budget cap ends the loop with `stopReason: budget`, and a model failure of the revision or its audit (`revisionFailureClass`: an error response, a timeout, an unusable or truncated answer, after any fallback) ends it with `stopReason: revision_failed`. Either way the last fully audited draft and its flags go to Gate 2, and an unaudited revision is in the ledger but not stored. Retrying the whole step would pay for every audit again, and a human reviews the draft at Gate 2 anyway. Abort, configuration, and programming errors still fail the execution. The step log names the failure class, never copy text.
- **Output (one commit, nothing written before it):** each revision as a `listing_copy` artifact under the verification step (`previousArtifactId` re-linked to the stored ID; its claims and `copy_generated` event via `storeListingCopy`), and each Q&A revision as a `qa_cards` artifact the same way (`storeQaCards`, `qa_cards_generated`); the verifier verdict on every claim of every audited draft, including the creative step's (`unsupported` with a `claim_support` flag, `flagged` with another verifier flag, else `supported`; `verifier_details = { promptVersion, auditArtifactId, pass, carried, flags[{ category, problem, suggestion }] }`; validator findings stay in `validator_details`); one `claim_audit` artifact (`claimAuditContentSchema`: prompt version, language, market, the rubric, `maxRevisionLoops`, `stopReason`, initial and final draft IDs, initial and final Q&A IDs (`initialQaArtifactId`, `finalQaArtifactId`, null without a Q&A step), one pass per loop `{ draftArtifactId, qaDraftArtifactId, revision, segments, auditedSegments, carriedSegments, modelRun | null, flags, dropped }` (a `qa` flag points at the pass's `qaDraftArtifactId`, any other at its `draftArtifactId`; the new fields read as null from audits stored before P3-03), `remainingFlags` = the last pass's flags, counts, `fallbackUsed`); and a `claims_audited` event with counts only (plus `finalQaArtifactId`). A flag is `{ source, category, code | null, artifactId, variant, segment, segmentIndex, claimId, problem, suggestion | null, carried }`. Step output IDs: the audit, then the revisions.
- **Gate 2 always opens:** `commit` never returns `releaseGate`, so the run stops at `claim_audit` even with zero remaining flags: Gate 2 is also where staged images are approved and where an operator signs off on the pack before export. For P3-08: list `remainingFlags` from the step's `claim_audit` (each names its `claimId`, the target of `decisions.target_kind = 'claim'`), show the final draft (`finalDraftArtifactId`) and the passes as history. Built in P3-08 (Gate 2 API below).
- **Idempotency:** `commit` writes only if the step has no `claim_audit` yet (inside the engine's completion transaction); a repeated commit returns the stored audit and revisions.
- **Q&A cards (P3-03, built):** audited in the same call as the copy under the `qa` variant (IDs `Q01…`), revised through P3-03's own function within the same loop, and stored in the same audit (see above). Gate 2 lists the final cards; the checklist and export read them.

**Publication checklist (P3-07).** Code: `apps/api/src/pipeline/checklist/` (`evaluate.ts` pure evaluator, `load.ts` database loader); result contract in `packages/shared/src/publication-checklist.ts`. Code only, no model call. Evaluated after Gate 2, when the export (P3-09) builds the pack; the web app may evaluate it during Gate 2 as a preview.

- **Evaluator (`evaluatePublicationChecklist({ market, facts, copy, claimAudit, stagedImages })`):** pure and deterministic (no database, clock, or model); one result per profile item, in the profile's order. Details name keys, counts, and categories only, never fact values or copy text, so the result has no personal-data scope of its own. The output is parsed against the shared schema before it is returned.
- **Rules (`PUBLICATION_CHECKLIST_RULES_VERSION` 1):**
  - `fact_present`: **pass** when the run has a `verified` fact with the key, from the form, the walkthrough, or a Gate 1 decision (photo facts are presence counts, never a value), on the profile measure (`units.area`/`units.volume`/`currency`; for areas the fact's `basis`), with a value valid for the profile fact, and all such facts state one value. **Fail** otherwise (none, only off-measure or invalid values, or several different values). Not `not_applicable`. The copy is **not** required to mention the fact: the schema defines the rule as "has a verified value in the pack", and the pack shows it in the Verified Fact Sheet and the portal-fields JSON. Whether the final copy cites it is reported as `citedIn` (variants), for information only.
  - `staged_images_labeled`: **not_applicable** when Gate 2 approved no staged image; **pass** when every approved image's `staged_image` record has `disclosure = { label: "Virtually staged", visibleLabelRequired: true }`; **fail** when any lacks it (listed in `unlabeledArtifactIds`). The rule checks the records; rendering the label visibly on every approved image is the export's job.
  - `no_flagged_phrasing`: **fail** when the run has no claim audit or the audit's rubric did not include the category (nobody checked it). Otherwise every `remainingFlags` entry of the category must point at a claim of the final draft that Gate 2 decided: `accept` (approved as written, an operator override listed in `acceptedClaimIds`), `edit` (rewritten; not re-audited), or `remove`. In a category of `NON_OVERRIDABLE_PHRASING_CATEGORIES` (`exclusionary`: equal-treatment risk) an `accept` is still recorded but keeps the item **failed**; only `edit` or `remove` clears it. A flagged claim without a decision, or a flag whose claim is not in the final draft, keeps the item **failed** (`unresolvedClaimIds`). Not `not_applicable`.
  - Unknown rules: the definition loader rejects them at boot (test in `loader.test.ts`); the evaluator's exhaustive switch throws for an unvalidated profile, so no item is skipped. A new rule kind breaks the typecheck until the evaluator and the result schema implement it.
- **Result (`publicationChecklistResultSchema`):** `{ schemaVersion: 1, rulesVersion, market { id, version }, items[], summary { readyToPublish, counts { items, pass, fail, notApplicable } } }`. Every item has `{ id, label, rule, status: pass | fail | not_applicable, detail }` plus its rule's evidence: `fact_present` → `fact, factIds, citedIn`; `staged_images_labeled` → `stagedArtifactIds, unlabeledArtifactIds`; `no_flagged_phrasing` → `category, audited, unresolvedClaimIds, acceptedClaimIds, editedClaimIds, removedClaimIds`. The schema refuses a status its evidence contradicts and counts or `readyToPublish` that do not match the items.
- **Failure policy (v1):** a failing item does **not** block export. `readyToPublish` is `true` exactly when no item fails (`not_applicable` does not count against it). Blocking would dead-end a run whose facts can no longer change after Gate 1 (e.g. no verified energy label); the checklist assists the agent and does not certify compliance (product §6). Gate 2 completeness (every flag and staged image decided) is P3-08's export block, separate from this.
- **Loader (`loadPublicationChecklistInput(db, markets, { run, approvedStagedArtifactIds, claimDecisions })`):** the caller passes Gate 2's decisions already resolved, so the loader does not depend on how P3-08 stores them: the approved `staged_image` artifact IDs, and `{ claimId, choice: accept | edit | remove }` for each decided claim of the final draft. It reads the run's market profile, its `verified` facts, the single `claim_audit` (none → `claimAudit: null`; several, an invalid one, or one made for another market throw), the final draft (`finalDraftArtifactId`, a `listing_copy` of the run) and its `claims` (segment variant and stored `fact_ids`), and the approved images' disclosures in `integrity_checks` manifest order. It throws `PublicationChecklistInputError` when the inputs do not fit the run: a decision on a claim outside the final draft, two decisions for one claim, decisions without an audit, an approved image that is not a `finalStagedArtifactId` of the run's single integrity record, or one approved twice. A staged record without a readable disclosure is passed on as `disclosure: null`, so the item fails visibly instead of the export crashing.
- **For the export (P3-09):** call the loader with Gate 2's resolved decisions, then the evaluator; render every item (label, status, detail) in the HTML pack, with a "not ready to publish" notice while `readyToPublish` is false and the `acceptedClaimIds` overrides named, and put the result object unchanged into the portal-fields JSON (`publicationChecklist`). Show every `fact_present` fact in the fact sheet and the portal fields, and the visible `disclosure.label` on every approved staged image, so the checked items hold in what is rendered. **Q&A (P3-03):** the loader adds the final Q&A cards' answer claims (`claim_audit.finalQaArtifactId`, variant `qa`) to the copy segments, and Gate 2 decisions may name them (a `remove` on any answer counts for every claim of its card, the Gate 2 drop rule); the export derives `accept` / `edit` from the pack's Q&A segments as from copy segments, so a `qa` flag is resolved by its decision like a copy flag and `citedIn` can list `qa`; a decision on a claim outside both final artifacts still throws.

**Gate 2 API (P3-08).** Code: `apps/api/src/gates/claim-audit.ts` (service) and `routes.ts` (shared with Gate 1), mounted in `createApp` at `/api/runs` behind `requireUser`, `requireJsonBody`, and the Origin guard; contracts in `packages/shared/src/gate2.ts`. Responses are `Cache-Control: no-store`; errors use `apiErrorSchema` (§14). Gate 2 decides the **final draft's flagged claims** and the **staged images the integrity check offers**, then the operator **approves the pack**, which is the only way out of the gate.

- **`GET /api/runs/:runId/gates/claim-audit`** → 200 `claimAuditGateResponseSchema`: `{ runId, runStatus, state, claimAuditArtifactId, finalDraftArtifactId, integrityChecksArtifactId, approvedPackArtifactId, outputLanguage, stopReason, passes[], counts { flaggedClaims, openClaims, offeredImages, openImages }, openCount, approval, variants[], facts[], images[], integrityFallbacks[], warnings[] }`. `state` has Gate 1's meanings (`not_reached` before the `claim_audit` artifact exists; `released` once approved). `stopReason` is the audit's (`clean`, `loop_limit`, `budget`, `revision_failed`); `passes` summarize the audit history (draft, revision, flag count, audited/carried segments). `finalQaArtifactId` and `qaCards` (P3-03): the final Q&A cards `{ card, question, dropped, segments }`, whose segments have the copy segments' shape (`paragraph` = card, `position` = position in the `qa` variant) and are decided the same way; empty without a Q&A step. `variants` are the final draft's `portal` and `social` segments, each with `claimId`, `index` (`claims.segment_index`), `position` in the variant, `paragraph`, `text`, `factIds`, `validatorResult`, `verifierVerdict`, its remaining `flags` (`source`, `category`, `code`, `problem`, `suggestion`, `carried`), and `decision` (null for unflagged segments and while open). `facts` are every fact the draft cites with Gate 1's `gateFact` shape (full provenance, for the evidence inspector). `images` are the offered staged images: `artifactId` (decision target, the file to show), the original `materialId`, `operation { id, kind }`, `disclosureLabel`, stored size, `integrity { outcome, aspectRatioChange, classes[{ label, originalCount, editCount, worstMatchedIoU }], attempts[] }` (each attempt: status, its `stagedArtifactId`, passed, failed classes, privacy result, unchecked target, reason code), and `decision`. `integrityFallbacks` are the staged photos with `fallback_original` (material, operation, attempts), so the UI can say "staging rejected by the integrity check". `warnings` are computed from the current decisions (below).
- **`PUT .../claims/:claimId/decision`** with `{ choice: 'accept' }`, `{ choice: 'edit', text }`, or `{ choice: 'remove' }`; **`PUT .../images/:artifactId/decision`** with `{ choice: 'accept' | 'reject' }`; **`POST .../approve`** with no body or `{}`. Strict objects. All three return the GET body. Errors: 400 `validation_failed` (body or path), 400 `claim_edit_rejected` with `findings` (the claim validator's findings on the edited text), 401 `unauthenticated`, 403 `forbidden_origin`, 404 `not_found` (unknown run, another user's run — never 403 — a claim without remaining flags, or an artifact that is not an offered image, e.g. a failed attempt or a fallback photo's edit), 409 `gate_not_open` (not reached, released, or failed there), 409 `gate_decisions_pending` (approve while anything is open), 415 `unsupported_media_type`.
- **Decisions** (`gate = claim_audit`, one row per target, `upsertDecisions`): a **flag** is decided per claim, because one claim can carry several flags and decisions are unique per target; one decision covers all of the claim's flags. Mapping onto `DECISION_CHOICES`: flag approve → `accept`, edit → `edit` (`target_kind = 'claim'`, `edited_value = claimEditSchema { text, validation }`), remove → `remove`; staged image approve → `accept`, reject → `reject` (`target_kind = 'artifact'`, the `finalStagedArtifactId`); the sign-off → `accept` on `target_kind = 'artifact'` with the `claim_audit` artifact's ID. No enum or schema change. Rows of any other shape (a `reject` on a claim, an edit without a valid stored value) read as open. Unflagged segments get no decision and are published as written. While open, decisions can be changed; repeating one writes nothing and keeps `decided_at`.
- **Edit:** the text replaces the segment's text; whitespace is collapsed and trimmed like stored copy (1–2,000 characters). The citations stay the claim's own fact IDs (the operator cannot re-cite: a changed citation would need the catalog and the verifier again). The text must pass `validateClaims` against the run's facts in the draft's language (numbers, units, approximation, ranges); otherwise 400 with the findings and nothing is stored. The verifier (model) is not re-run on edited text: the operator takes responsibility for wording, the validator for numbers and citations. The draft artifact and its `claims` rows are never modified.
- **Q&A answers (P3-03):** a flagged answer segment is accepted, edited (validated with `variant: 'qa'` against its own citations), or removed exactly like a copy claim; the question is context and cannot be edited. **Removing any flagged answer segment drops the whole card** (decided in the P3-03 review): the verifier flags a question's problem on the card's first answer, so removing just that answer would still publish the question; cards are optional, so dropping fails safe. The response marks such a card `dropped: true`, its other flagged answers no longer count as open, and the pack omits the card and lists all of its claims in `removedClaimIds`; the checklist loader treats every claim of a card with a `remove` decision as removed too, so the checklist and the pack agree. Accepting a flagged answer keeps the card (an `exclusionary` accept still fails the checklist). Q&A removals raise no warnings: no fact must appear in Q&A.
- **Remove:** the segment is dropped from the published copy. Not blocking, but `warnings` reports `market_fact_unmentioned { variant, factKey, required, removedClaimIds }` for every market-profile fact that removed segments cited and no kept segment of that variant cites any more (mentions are citations), and `variant_empty` when every segment of a variant is removed (the export then publishes no text for it). The publication checklist (P3-07) judges the pack; the UI should show these before approval.
- **Approval and resume (explicit sign-off, also when there is something to decide):** deciding the last item never resumes the run. `POST .../approve` runs in one transaction: ownership check, `lockRun`, gate check; refuses with `gate_decisions_pending` while any flagged claim or offered image is undecided; otherwise records the sign-off decision, writes the `approved_pack` artifact, appends `gate_decided` (IDs and counts only), and calls `resumeAfterGate(runId, { gate: 'claim_audit', tx })`, so the release, `awaiting_gate → running`, and the export job commit together or not at all. Two concurrent approvals serialize on the lock: exactly one resumes, the other gets 409 `gate_not_open`; a decision racing an approval either lands first (and is in the pack) or gets 409. Why not Gate 1's auto-resume: Gate 2 is a sign-off by definition (P3-06 opens it even with nothing to decide), so one trigger covers both cases with one UI flow; and the warnings a removal causes appear only after the decision, so auto-resuming on the last decision would export before the operator could see them or change their mind. The transactional and locking mechanics are Gate 1's.
- **What P3-09 reads:** the run's single `approved_pack` artifact (`approvedPackContentSchema`, step ID `gate:claim_audit`), written once at approval, nothing else for copy decisions: `variants` (`portal`, then `social`) with the published segments in draft order, each `{ claimId, index, paragraph, text, factIds, origin: unflagged | accepted | edited }` (edited text already substituted, removed segments absent, listed in `removedClaimIds`); `finalQaArtifactId` and `qaCards` (P3-03), the published cards in card order `{ card, question, segments: [{ claimId, index, text, factIds, origin }] }` (a dropped card is absent and all of its claims are in `removedClaimIds`; both fields default to null / empty for packs approved before P3-03); `images`, one per staged photo of the integrity record in its order, `{ materialId, operationId, integrityOutcome, offeredArtifactId, decision, publishedArtifactId }`, where `publishedArtifactId` (an accepted final image, else null) is the only staged image to export, labeled with its `disclosure.label` next to the original `materialId`; `warnings`; `approvedBy`, `approvedAt`; and the source artifact IDs (`claimAuditArtifactId`, `finalDraftArtifactId`, `integrityChecksArtifactId`). Photos not in the integrity record were never staged; P3-09 takes the photo set from the inventory and blurs the stored privacy masks. The decisions remain the audit record. The publication checklist loader's Gate 2 input (P3-07) comes from the same artifact: `approvedStagedArtifactIds` = the non-null `publishedArtifactId`s; `claimDecisions` = `accept` for segments with origin `accepted`, `edit` for `edited`, `remove` for each of `removedClaimIds` (unflagged segments have no decision).
- **For P4-07:** the files behind these IDs (original photo, staged image, mask overlay, transcript audio) are served by the Run API below; every URL is computed from IDs this response already returns, so the gate contracts did not change.

**Export (P3-09).** Code: `apps/api/src/export/` (`build.ts` loads and composes, `handler.ts` stores; `blur.ts`, `label.ts`, `images.ts`, `facts.ts`, `portal-fields.ts`, `html.ts`, `strings.ts`, `escape.ts`, `ids.ts`), registered in `worker.ts` as agent `exporter`; contracts in `packages/shared/src/export.ts`. Code only, no model call. It sits in `apps/api/src/export/` rather than `pipeline/` because it is backend-owned (task owners table) and model-free.

- **Inputs (`buildRunExport(deps, db, run)`):** the run's single `approved_pack` (none, several, an invalid one, another output language, or a `claimAuditArtifactId` that is not the run's audit for the pack's final draft and final Q&A cards → `NonRetryableStepError`); the single `photo_inventory`; the integrity record the pack names (required when the pack lists staged photos); the run's `verified` facts (including `gate_decision` facts); the project's title and office profile (agency name, contact block); and the publication checklist, computed with `loadPublicationChecklistInput` + `evaluatePublicationChecklist` from the pack exactly as P3-08 documents (`approvedStagedArtifactIds` = non-null `publishedArtifactId`s; `accepted` → `accept`, `edited` → `edit`, `removedClaimIds` → `remove`; a `PublicationChecklistInputError` → `NonRetryableStepError`). Decisions are never read directly. The checklist is evaluated here, not stored at Gate 2, and goes into the JSON unchanged.
- **Facts (`buildPortalFacts`):** every market-profile fact, in profile order, as a typed field (`enum`, `area` with unit and basis `{ id, label }`, `volume`, `integer`, `money` with the currency, `boolean`) with `status`: `verified` (exactly one value), `missing`, or `ambiguous` (several values; none published). A field takes exactly the facts the checklist's `fact_present` rule takes (verified, not from a photo, on the profile measure, valid for the fact), so a passing item always shows its value; a test pins the agreement. Verified `other:` facts are grouped like the copy catalog (`buildCopyFactCatalog`). Photo facts become **presences** (`key`, rooms `seenIn`, fact IDs) with no value at all: a photo count is never published.
- **Image order:** the inventory's photos by cover rank, then unclassified photos in upload order. A Gate 2-approved staged image takes its photo's place and its original follows it directly (side by side in the HTML). Files are `photo-NN.jpg` / `photo-NN-staged.jpg`, numbered by place in the export.
- **Privacy, fail-closed (`privacyPlan`):** `review` and `failed` photos are **not exported**; the pack lists them as "withheld: privacy check incomplete" by upload position. A `masked` photo is exported only after every region of every checked phrase is blurred; a `masked` photo without regions, a box outside the frame, or a mask that does not decode (`decodeSamMask`) or does not match its box size is withheld (`privacy_regions_invalid`). Each original is re-read and checked against the inventory's SHA-256 and frame (`readOriginals`), so the boxes land on the pixels SAM saw. A decode, blur, or encode failure withholds the photo (`blur_failed`); environment errors (missing binary, memory) propagate to the engine's retry. `clear` photos are copied byte for byte (already metadata-free, P2-05). A withheld original also withholds its staged image (`original_withheld`).
- **Blur method:** per region the SAM box padded by 10% of its longer side + 2 px (clipped), pixelated to ~8 blocks along the longer side (≥ 8 px per block), scaled back with nearest-neighbour, then Gaussian-blurred (sigma = half a block); only pixels inside the box are read, pixels outside are unchanged. The box, not the mask: the mask is a box-local raster, so the padded box covers every mask pixel plus a margin for SAM's edge error. Re-encoded as sRGB JPEG q85 mozjpeg without metadata.
- **Staged images (`isPublishableStaged`):** only `publishedArtifactId`, and only when the integrity record names it as the photo's `finalStagedArtifactId`, its last attempt is the passing check of exactly that image with `person` segmented and every privacy phrase at 0, its `staged_image` record links it to the inventoried original's material and SHA-256, and the original is privacy-`clear`. Otherwise the staged image is withheld (`staged_unverified`) and the original still exported. A missing file or checksum mismatch is a storage fault (`NonRetryableStepError`).
- **Burned-in label (`burnStagedLabel`):** a dark badge with "Virtually staged" in the bottom-left corner (~1/300 of the shorter side per glyph unit, 2.5% margin, shrunk for narrow images, refused below legibility → `label_failed`). The text is SVG **strokes**, not `<text>`: the slim production image has no fonts, so librsvg would render text as nothing. Order: composite onto the decoded pixels, encode once (JPEG q85 mozjpeg), and the encoder writes P3-04's XMP packet (IPTC `DigitalSourceType = compositeWithTrainedAlgorithmicMedia`) into that output; no other metadata.
- **HTML (`renderListingPackHtml`):** one self-contained, print-ready file: `<html lang>` = output language, inline CSS with `@page { size: A4 }`, a CSP meta (`default-src 'none'; img-src data:; style-src 'unsafe-inline'`), no script. Sections: header (agency, title, approval time in UTC, market), the **not-ready notice** while `readyToPublish` is false (failing item labels plus the operator overrides: segments approved as written, quoted, and rewritten ones). A segment approved as written whose remaining flags include a category of `NON_OVERRIDABLE_PHRASING_CATEGORIES` (`exclusionary`), or that a failing `no_flagged_phrasing` item lists as accepted, is never shown as an allowed override: it is rendered as a failure in the notice ("approved as written, which is not allowed for exclusionary language: edit or remove"), read from the item `status` and `isOverridablePhrasingCategory`; a market without such an item (`nl`) still gets the notice, titled "Review before publishing". The flag categories come from the claim audit the pack names, copy (portal paragraphs, social caption, or "every segment removed"), buyer Q&A (`<section id="qa">`, a `<dl>` of question and answer, only when the pack has cards; accepted and edited answers are listed with the copy's overrides), fact sheet (profile table, other facts, presences), photos (staged images with the visible label and their originals; blurred photos captioned; withheld list), publication checklist (label, status, detail; overrides here when ready; Gate 2 warnings), footer (contact block, run ID). Every interpolated string goes through `escapeHtml` (`& < > " '`); no template library. Fixed wording in `en` and `nl` (`strings.ts`), other languages fall back to English; market labels and checklist details stay as their sources write them. **Images are embedded as data URIs**: the pack is one download that prints alone, and P4-08 can serve it without a file route; the cost is ~4/3 of the image bytes again in the HTML.
- **Portal fields (`portalFieldsSchema`, `portal-fields.json`, `schemaVersion` 2 since P3-03 added `qaCards`):** `{ schemaVersion, formatVersion, runId, approvedPackArtifactId, approvedAt, market { id, version }, outputLanguage, facts { profile[], other[], presences[] }, copy { portal, social } (each `text`— segments joined by a space, paragraphs by a blank line — and`segments` with claim ID, index, paragraph, text, fact IDs, origin), qaCards[] (`question`, `answer`= segments joined by a space,`segments` with claim ID, index, text, fact IDs, origin), images[] (`kind: original | staged`, position, file name, file artifact ID, material ID, size, SHA-256; originals with cover rank, subject, privacy status and blurred-region count, and the staged file name; staged with the `staged_image`ID, operation,`disclosure { label, burnedIn: true, digitalSourceType }`, and the original's file name), withheld[] (material, upload position, kind, reason), publicationChecklist }`. Validated before it is stored.
- **Determinism:** no clock (the approval time comes from the pack; the HTML formats it in UTC by hand), stable orders everywhere (profile order, catalog order, cover rank, upload order), numbers printed exactly as verified (no locale formatting; `nl` uses a decimal comma), JSON serialized from the parsed schema output (zod builds objects in shape order) with 2-space indentation, and **content-derived artifact IDs** (`exportArtifactId(runId, fileName)`: a UUIDv8 from SHA-256), so the JSON can name each image's file artifact and still be byte-identical when rebuilt. `insertArtifact` accepts a caller-chosen `id` for this. The same stored artifacts give byte-identical HTML and JSON and, on one machine, identical images (the integration test rebuilds and compares every file). sharp's output can differ across CPU architectures (P3-05), and the HTML embeds the images, so across platforms only the structure is equal.
- **Output (one commit):** files are written to storage under `newRunArtifactStorageKey` before the transaction and deleted again on any failure. Then one artifact per file with the file attached (`export_html`, `export_portal_fields`, `export_image`; content `exportFileContentSchema { role, fileName, sizeBytes, sha256 }`), the `export` manifest (`exportManifestContentSchema`: pack and inventory IDs, `readyToPublish`, files — HTML, JSON, then images — with artifact ID, role, name, MIME type, size, SHA-256, and counts), and a `pack_exported` event with counts only. A failing checklist does not block the export (P3-07). **Idempotency:** `commit` writes only if the step has no `export` manifest yet; a repeated commit keeps the stored export and deletes the new files. Project deletion returns every export file's storage key (they are run artifacts).
- **For P3-10 and P4-08:** run the export through the engine (registered handler), or call `buildRunExport({ storage, markets }, db, run)` for the in-memory files. To read a stored export: the run's `export` manifest lists every file; each artifact's `storageKey` holds the bytes. The Run API below serves them (P4-08): the HTML as is with the same CSP as a header, the JSON as a download.

**Run API (P4-05 … P4-08 backend).** Code: `apps/api/src/run-api/` (`service.ts` reads, `routes.ts` (`addRunReadRoutes`: the read routes the owner API and the Demo API below both mount, parameterized by `RunReadAccess`: how a run is resolved and how responses are cached), `event-stream.ts` + `event-source.ts` SSE on `sse.ts` (the SSE plumbing shared with the demo replay: headers, `retry:`, heartbeat, lifetime, per-key cap, backpressure, cleanup), `send-file.ts` + `range.ts` files, `mask.ts` overlay), mounted in `createApp` at `/api/runs` (before the gate router, whose `router.use` would otherwise run on these requests) and `/api/projects`; contracts and the URL builders in `packages/shared/src/run-api.ts` (path segments `encodeURIComponent`-encoded; `runEventsUrl` throws on an `after` that is not a non-negative integer). Every route is behind `requireUser` per route (not `router.use`, so the routers can share their prefixes); a missing ID and another user's ID both answer 404 `not_found`, never 403. JSON responses are `Cache-Control: no-store`; errors use `apiErrorSchema` (§14). All routes are GET (HEAD works too), so the Origin guard and `requireJsonBody` do not apply.

- **`GET /api/runs/:runId`** → 200 `runSnapshotSchema`, read in one `repeatable read, read only` transaction (ownership included): `{ id, projectId, status, serviceId, serviceVersion, marketProfileId, marketProfileVersion, outputLanguage, gate, currentStepId, failureReason, createdAt, startedAt, finishedAt, updatedAt, costUsd, costCapUsd, lastEventSeq, maxExecutionsPerAttempt, steps[], export }`. `gate` is the open gate (null unless `awaiting_gate`); `costUsd` sums every ledger row of the run; `costCapUsd` is the definition's `budget.max_cost_usd_per_run` (null if the run's definition version is no longer loaded); `lastEventSeq` is the newest event in the same snapshot, so opening the stream at it neither misses nor repeats a change. `steps` are the definition's steps in order (then any stored step the definition no longer lists), each `{ stepId, agent, gateAfter, status, attempt, attempts, executions, totalExecutions, costUsd, startedAt, finishedAt, gateReleasedAt, error }`: `status` is `pending` until the first attempt is scheduled, then the latest attempt's (`queued` also while a failed execution waits for its retry, with `error` saying why); `executions` counts the latest attempt (at most `maxExecutionsPerAttempt`); `costUsd` covers all attempts; `gateReleasedAt` marks a passed gate. `export` is `{ manifestArtifactId, readyToPublish, fileCount }` once the export step stored its manifest, else null. Errors: 400 `validation_failed`, 401 `unauthenticated`, 404 `not_found`.
- **`GET /api/projects/:projectId/runs`** → 200 `projectRunsResponseSchema` `{ runs: runSummarySchema[] }`, newest first; a summary is the snapshot's run fields without steps (`costUsd` from one grouped ledger query). 404 for another user's or an unknown project. B1's project router mounts at the same prefix: keep this router's per-route guard (or move the route there).
- **`GET /api/runs/:runId/events`** (`text/event-stream; charset=utf-8`): the stored `run_events` after a cursor, then new ones as they commit. Cursor: the `Last-Event-ID` header (sent by `EventSource` on reconnect) wins over `?after=<seq>` (the snapshot's `lastEventSeq`, for the first connect, since `EventSource` cannot set headers); neither → from the first event; both validated as `runEventCursorSchema` (400 otherwise). Ownership is checked once, at connect (404 is JSON, before any stream byte). Each event is a default `message` with `id: <seq>` and `data` = `runStreamEventSchema` `{ seq, type, payload, occurredAt }`, the stored row unchanged (payloads are the §9 schemas plus `runStatusChangedPayloadSchema`); clients `safeParse` it and refetch the snapshot on an unknown type. **Rows are streamed raw:** the stream's source reads `seq, type, payload, occurred_at` without the repository's type and payload parsing, so one row today's schemas reject (an older or newer event shape) is delivered as stored instead of failing the stream at the same seq on every reconnect. **A cursor beyond the run's `last_event_seq`** (a stale or foreign `Last-Event-ID`, a hand-made `after`) is clamped to it and announced with `event: resync` + `runStreamResyncSchema { lastEventSeq }`: the stream continues from the real head (so later events are not skipped) and the client refetches the snapshot, since its state cannot be trusted. The stream opens with `retry: 3000`, sends `: ping` comments every 15 s, and when the run is `completed` or `failed` and every event up to the run's `last_event_seq` was sent, it sends `event: end` with `runStreamEndSchema { status, lastEventSeq }` (always the run's `last_event_seq`) and closes. The client must call `close()` on `end` (otherwise `EventSource` reconnects, gets `end` again, and loops every 3 s); after resuming a failed run it opens a new stream at its last seq. Headers: `Cache-Control: private, no-cache, no-transform` (`no-transform` makes Caddy's `encode` skip the response, so nothing is compressed or buffered; Caddy's `reverse_proxy` already flushes `text/event-stream` immediately), `X-Accel-Buffering: no`, `nosniff`; the API has no compression middleware.
  - **Live cost:** no new event or periodic snapshot. The engine already appends `usage_recorded { stepId, stepCostUsd, runCostUsd }` after every metered call (and `step_completed` / `step_failed` carry the totals), so spend moves call by call; costs are absolute totals, so applying an event twice is harmless.
  - **Short poll, not LISTEN/NOTIFY.** Each stream polls every 1 s: one primary-key read of `runs (status, last_event_seq)` and, only when the seq moved, `run_events where seq > cursor and seq <= last_event_seq` (batches of 200, primary-key range). Reading up to the run row's `last_event_seq` is safe because the counter and the event commit together and seq is gapless per run, so no event can commit later below the cursor. Why poll: LISTEN needs a dedicated connection held outside the pg pool, reconnect handling, and a catch-up query after every reconnect anyway (notifications sent while disconnected are lost), plus a `pg_notify` in `appendRunEvent` or a trigger (a migration); for one VPS with a handful of open monitors, two indexed queries per stream per second through the shared pool cost nothing and the 1 s latency is invisible next to steps that take seconds. Trade-off: up to 1 s delay and constant small load while a tab is open (also at a gate, which can wait for hours); LISTEN/NOTIFY can replace the source (`RunEventSource`) later without touching the stream format.
  - **Limits:** a stream lives at most 1 hour (`maxLifetimeMs`), then closes without `end`; `EventSource` reconnects with `Last-Event-ID`, which re-runs the session and ownership check (a session that expired or a project that changed hands stops streaming within the hour). At most 5 open streams per user (`maxStreamsPerUser`, in-process like the rate limits): one more gets 429 `too_many_streams` before any stream byte. Both are `RunEventStreamOptions`.
  - **Resources:** a stream holds no connection between polls, owns one heartbeat interval, one poll timer, and one lifetime timer, and awaits `drain` when the socket buffer is full (the wait also ends on close; heartbeats are skipped while the buffer is full). The `close` listener is registered first and `res.destroyed` / `writableEnded` checked right after, so a client that left during the route's ownership query never gets timers or queries. Client disconnect, the end event, the run disappearing (project deleted: the stream just ends), a query error (logged; the browser reconnects with `Last-Event-ID`), or shutdown clear both timers; an in-flight query finishes and is discarded. `server.ts` aborts `runs.shutdownSignal` after `server.close()`: open streams end and their keep-alive sockets are closed, otherwise `close()` would wait for them.
  - **Replay (P4-09):** the format is the stored rows with their `occurredAt`, so the public replay can emit the same messages from a completed run with the original spacing.
  - **Web client (P4-05):** `/runs/[runId]` keeps the snapshot in the TanStack Query cache and applies events to it (`apps/web/src/lib/run-monitor.ts`); a run that is `completed` or `failed` opens no stream and is re-read on mount and window focus, so a resume done elsewhere is noticed and the stream reopens at the new `lastEventSeq`; `resync`, an unknown event, or a sequence gap triggers a snapshot refetch (a refetch that joined an older in-flight request is repeated once), and `end` shows the terminal state at once and then confirms it with a final snapshot.

Conditional requests: `If-None-Match` → 304. **Range** (single range, RFC 9110): 206 with `Content-Range`; a well-formed range starting at or past the end → 416 `range_not_satisfiable` with `Content-Range: bytes */<size>` and `Cache-Control: no-store` (an error for that request, never cached; also on the demo and project material routes); a malformed spec, another unit, or several ranges are ignored (200, as Express's `send` does); a stale `If-Range` → 200. Range-capable files carry `Cache-Control: private, no-cache, no-transform`, so Caddy never re-encodes a 206. Sizes come from `storage.stat`; the file is opened before any file header is set, so a database row whose file is missing is a clean 500 (logged with the key) without stale `ETag` or `Content-Range`.

The masks are those of the observation with the fact's key in the photo with the fact's `materialId` (§5 Vision); each box-local one-bit raster is decoded with `decodeSamMask` and placed at its box. **Format (`RUN_FACT_MASK_PNG`):** an RGBA PNG exactly the stored photo's width × height (the frame of the photo file and of SAM's boxes), mask pixels opaque white `(255,255,255,255)`, all others `(0,0,0,0)`, the union of the observation's masks. The UI lays it over the photo at the same size and uses it as a CSS `mask-image` over a theme-coloured layer. Full frame rather than box-local plus box: one element with no coordinate math, and PNG deflate makes the empty area almost free. A region without a mask (beyond the evidence cap), with a box outside the frame, a raster of the wrong size, or an undecodable payload is skipped (logged as a count); 404 when nothing is left, when the fact has no `maskArtifactId` (draw `source.region` instead), or is not a photo fact. `ETag` `"mask-v1-<factId>-<inventoryArtifactId>"`, decided from the fact row alone, so `If-None-Match` (`*`, lists, `W/`) answers 304 before any mask is decoded; encoded with sharp off the event loop.

- **Decisions file (`decisions.json`, format version 1, strict).** Run, fact, and claim IDs exist only per run, so decisions address what a project keeps stable:

  - `claimAudit.images { default, decisions[] }`: one entry per project photo file name, `choice: "accept" | "reject"`, for the staged image the integrity check offers for that photo. `default`: `accept`, `reject`, or `fail`.

Named images are hashed as their names, so a cassette recorded on a Mac replays in CI. The summary reports images sent without a name (0 in the demo). The voice memo matches by its fixed name (`voice-memo.wav`) as in P2-06, because the TTS walkthrough a run is recorded from is not committed; the demo project carries a 1-second silent stand-in, and recording or a meaningful live run passes the local TTS file with `--voice-memo`.
- **Summary** (printed and `summary.json`): run ID, mode, cassette, status and failure reason, per-step status, attempts, executions, and cost; per photo (inventory order, by file name) the vision subject, furnishing, cover rank, and privacy status and the staging outcome with its operation and skip or failure reason; Gate 1 conflicts and each decision with its origin (decisions file or default policy); buyer Q&A cards per stored set; Gate 2 stop reason, passes, flagged claims, each claim and image decision (flags as `source/category/code`, never their text), integrity fallbacks, warnings; unused decisions; the export files, `readyToPublish`, checklist item statuses, withheld count; cost from the usage ledger (run total, cap, calls, per model; exact decimals in the JSON); in fixtures and record modes the network counters.
- **Real definition:** since P3-03 the CLI runs `listing-launch` v1 as loaded, `qa_cards` included (the temporary P3-10 filter `definition.ts` is gone). The summary lists every stored set of Q&A cards (step, revision, cards, answer segments, dropped cards, validator failures) and the export's Q&A card count; Gate 2 claim decisions and the decisions file address Q&A answers as `{ variant: "qa", position }` (position across all cards).
- **Development seed (`npm run dev:seed`) and replay worker (`npm run dev:worker:replay`).** Real runs for the web UI's smoke tests and the Playwright E2E (P5-05), with zero model calls. Code: `apps/api/src/cli/` (`dev-seed.ts` entry, `dev-seed-run.ts` `seedDevRun`, `dev-worker.ts` entry, `replay-worker.ts`); `executePipeline` gained `stopAtGate`, and `fixtureMatchOptions` is shared by every replay of a project's cassette. Proven by `dev-seed.integration.test.ts` (api-integration; Docker and ffmpeg).
  - **Command:** `npm run dev:seed -- --owner <email> [--stop-at gate1|gate2|completed] [--timeout-minutes <n>] [--verbose] [project-dir]`. Default project `fixtures/projects/synthetic-walkthrough`, default stop point `completed`. It runs the same flow as `demo:seed` (fixture mode, the project's cassette through MSW, scripted decisions) against `DATABASE_URL` and `STORAGE_DIR`, and prints the project ID, run ID, state, calls (metered, from the cassette, live), and the web URLs: `/runs/<id>`, `/runs/<id>/conflicts` (Gate 1), `/runs/<id>/review` (Gate 2), `/runs/<id>/pack` (completed only), on `APP_ORIGIN`. Exit codes: 0 seeded, 1 the run did not end where asked (or had a live or unmatched request), 2 invalid invocation, environment, project, or account, or production.
  - **Owner:** an existing account found by email (case-insensitive). The seed never creates accounts and never sets or prints a password; an unknown email exits 2 with "register it in the web app first".
  - **Stop points:** `gate1` leaves the run `awaiting_gate` at `fact_conflicts` before any Gate 1 decision (every conflict open); `gate2` applies the scripted Gate 1 decisions and leaves it at `claim_audit` before any claim or image decision (nothing decided, nothing approved; the synthetic recording has no flagged claim, so what is open is its one staged image); `completed` applies both gates and the export. A seeded run is an ordinary run: its gate state is the same rows the API reads, and a decision through the API resumes it through the normal engine.
  - **Continuing a seeded run without live calls (approach a).** The seed's own jobs go to a pg-boss schema of that invocation (`pgboss_dev_seed_<random>`, dropped at the end), so a running worker can never pick one up. A run waits at its gate with no job queued; the decision made through the API enqueues the next step in the default `pgboss` schema, which only a worker started with `npm run dev:worker:replay -- [project-dir]` should be working, **instead of** `npm run dev:worker` (both would work the same queue, and the live one would make live calls). That worker registers the production step handlers (`createStepHandlers`) but builds its Meta clients with the replay's placeholder key, behind MSW serving the project's cassette (fixed to replay mode; the real `MODEL_API_KEY` is never read): an unrecorded request fails the step with a 404 naming it, and any other host gets a network error. It names the project's photos in the replay the way the seed did (`registerProjectPhotos` prepares the same files with the same sharp code; deterministic on one machine), so no database lookup is needed.
  - **What a replay can follow.** Later requests embed the decided facts, so Gate 1 must be decided like the script (`decisions.json`): the seed prints the exact decisions for a `gate1` run. Any other decision changes the creative request, which the cassette does not hold, and the run fails with the unmatched request in its failure reason; still zero live calls. Gate 2 decisions are free: only the export follows, and it calls no model. A run of another project than the worker's `project-dir` fails the same way.
  - **Never in production, three ways.** Both entries check `NODE_ENV=production` first, before arguments or environment are read, and exit 2 (`assertNotProduction`; `seedDevRun` and `startReplayWorker` check again). They import MSW, a dev dependency that the production image does not install (`worker.ts` stays free of it, as `meta/replay.ts` requires), and need the committed `fixtures/`, which that image does not contain. There is no flag or environment variable that turns replay on in `worker.ts`.
  - **Daily cap.** The seed and the replay worker run under `DEV_REPLAY_DAILY_CAP_USD` (9999.99, the largest the amount format allows) instead of `DAILY_BUDGET_USD`: they make no live call, and an already-full real cap must not fail a replay. Their usage is still written to the ledger (the run monitor shows it) and, because a dev account is not the demo owner (§10), it counts toward the day's total for live runs in the same database: at about 0.45 USD as if live per completed run, eleven seeds fill the default 5.00 dev cap. This is the safe direction and local only; raise `DAILY_BUDGET_USD` or use a fresh database if it gets in the way. An exact exclusion needs a marker on the ledger rows (a schema change), not done.

**Model and effort defaults (P1-03).** The efforts above are the service-definition defaults (§7), chosen from measurements on a reconciliation-sized synthetic input (~4.3k input tokens, four planted defects) and one verification-sized call; details in [model-notes.md](./model-notes.md#p1-03--wonder-10-cost-and-latency).

- Wonder `low` caught every planted defect in reconciliation ($0.076, 13.7 s) and verification ($0.05, 12.5 s). `medium` (+25% cost) and `high` (+70%) added nothing and produced slightly messier output, so judgment steps start at `low`.
- Spark `medium` matched Wonder on reconciliation at 46% of the cost but 60% more latency (6× the reasoning tokens). It is the fallback for both judgment steps, and promoting it to primary is a definition change if the budget tightens.
- Spark steps (extraction, classification, Q&A) use `low`. Creative copy uses `medium` because a segment that fails the validator or verifier costs a revision loop (~$0.08). P3-01 confirms this setting with the validator pass rate.
- Every step sets `max_output_tokens` at about 4× its expected output, so one runaway reasoning call cannot consume the run budget. Exception, measured in P2-07: fact extraction answers with ~4.4k tokens on a 3-minute walkthrough after ~4–5.5k reasoning tokens at `low`, so 8,000 truncated the answer; it is 14,000 (~1.7× the measured 8.4k, worst case $0.062 per call).
- Reconciliation constraint for P2-09: every model verified a basis-less gross area (104 m²) as a fact under a different free-text key each time. `basis` must therefore be limited to the market profile's bases plus an explicit "other/unspecified" value, and keys must be normalized against the profile so that such areas can never be cited as living area. Done: P2-07 constrains keys and bases, and P2-09's verified values carry a cited candidate's key exactly (see Reconciliation above).

## 6. Provenance: "no source, no claim"

1. The creative step receives only the verified facts (after Gate 1) and must return copy as structured segments: `{ text, fact_ids[] }` (P3-01: short catalog IDs in the model's answer, stored fact IDs in the artifact and `claims`).
2. A code-level validator rejects any segment with empty or unknown `fact_ids`, and compares every number in the text to the cited fact exactly. This runs before any model-based verification.
3. The verifier judges semantic support: does the cited fact actually justify this wording?
4. In the UI, clicking a claim shows its evidence: the form field, the transcript turn (with timestamp and audio playback from that point), or the photo with its SAM mask overlay.

## 7. Definition formats

Files: `definitions/services/<id>.v<version>.yaml` and `definitions/markets/<id>.v<version>.yaml`; the file name must match the content's ID and version. Schemas: `packages/shared/src/definitions.ts` (shared because the web fact form is generated from the market profile schema). Loader: `apps/api/src/definitions/` (P2-02).

- **Parsing:** YAML 1.2 core schema with duplicate keys, unknown tags (every parser warning), merge keys, and aliases rejected. All objects are strict zod objects, so an unknown key is an error.
- **Errors** name the file, line and column, the path inside the document, and the problem, e.g. `markets/nl.v1.yaml:12:66: market.facts[1].basis: Area basis "gross" is not listed in area_bases`. One error lists every problem in every file.
- **Boot:** `server.ts` and `worker.ts` call `bootDefinitions` before opening the database pool, port, or queue; any problem is logged as fatal and the process exits with code 1. Boot also requires the published `listing-launch` v1, `international` v1, and `nl` v1 to be present. The directory defaults to the repository's `definitions/` (resolved from the source location; the API image copies it to `/app/definitions`) and can be overridden with `DEFINITIONS_DIR`.
- **Versions are immutable** once runs reference them: a change is a new file with the next version. The registry is frozen and looked up by `getService(id, version)` / `getMarket(id, version)`.

Service definition (`listing-launch.v1.yaml` without comments; steps read model, effort, and token cap from here, never from code):

```yaml
service:
  id: listing-launch
  version: 1
  name: Listing launch
  inputs:
    - key: photos
      type: images
      min: 10
      max: 30
      required: true
    - key: voice_memo
      type: audio
      max_seconds: 600
      required: true
    - key: facts
      type: form
      schema: from_market_profile
      source_of_truth: true
      required: true
  steps:
    - id: intake
      agent: intake
      model: muse-voice-transcribe-1.0
      transcription_mode: DIARIZATION
      max_turn_seconds: 30
    - id: fact_extraction
      agent: extractor
      model: muse-spark-1.3
      reasoning_effort: low
      max_output_tokens: 14000
    - id: vision_inventory
      agent: vision
      model: muse-spark-1.3
      reasoning_effort: low
      max_output_tokens: 4000
      segmentation_model: sam-3.1
      max_evidence_masks: 12
      privacy_phrases: [person, license plate]
      classification_long_edge_px: 1024
    - id: reconciliation
      agent: reconciler
      model: muse-wonder-1.0
      reasoning_effort: low
      max_output_tokens: 12000
      fallback_model: muse-spark-1.3
      fallback_reasoning_effort: medium
      gate_after: fact_conflicts
    - id: creative
      agent: creative
      model: muse-spark-1.3
      reasoning_effort: medium
      max_output_tokens: 16000
    - id: qa_cards
      agent: qa_writer
      model: muse-spark-1.3
      reasoning_effort: low
      max_output_tokens: 8000
    - id: staging
      agent: stager
      image_model: muse-image-1.0
      max_staged_images: 3
    - id: integrity
      agent: integrity_checker
      segmentation_model: sam-3.1
      fixed_elements:
        - { phrase: window, occlusion_tolerant: false }
        - { phrase: door, occlusion_tolerant: true }
        - { phrase: radiator, occlusion_tolerant: true }
      min_iou: 0.75
      min_containment: 0.85
      min_area_ratio: 0.4
      max_aspect_ratio_change: 0.03
      edit_privacy_phrases: [person]
    - id: verification
      agent: verifier
      model: muse-wonder-1.0
      reasoning_effort: low
      max_output_tokens: 12000
      fallback_model: muse-spark-1.3
      fallback_reasoning_effort: medium
      max_revision_loops: 2
      gate_after: claim_audit
    - id: export
      agent: exporter
  budget:
    max_cost_usd_per_run: '1.00'
```

- Steps are a union on `agent` (`intake`, `extractor`, `vision`, `reconciler`, `creative`, `qa_writer`, `stager`, `integrity_checker`, `verifier`, `exporter`); each agent allows only its own fields. Buyer Q&A is its own step, so cut level 1 removes one entry.
- Every model ID (`model`, `fallback_model`, `segmentation_model`, `image_model`) must exist in `PRICE_TABLE`, so an unpriced model fails at boot rather than at the first call. `-contributor` IDs are rejected.
- Language-model steps require `reasoning_effort` (validated by `metaReasoningEffortSchema`, the same set for Spark and Wonder) and `max_output_tokens` (bounds the worst-case reasoning cost of one call; per photo in vision inventory). Efforts are rejected on models not billed per token. `fallback_model` must differ from `model` and requires `fallback_reasoning_effort`.
- Step IDs, input keys, and gates are unique; `gate_after` is a known gate.
- The vision step requires `max_evidence_masks` (0–100: per run, the cap on SAM evidence requests and on stored evidence masks), `privacy_phrases` (1–5 unique SAM noun phrases, segmented on every photo, uncapped), and `classification_long_edge_px` (256–4096: Spark's input resolution). Phrases are validated like `assertSamPhrase` (`samPhraseSchema`: one noun phrase, ≤ 80 characters, no list or token characters). The last two were added to `listing-launch` v1 in place in P2-08, before any run existed.
- The intake step requires `transcription_mode` (`ENDPOINTING` or `DIARIZATION`; `PUSH_TO_TALK` returns no turns and is rejected) and takes an optional `max_turn_seconds` (5–600; omitted = turns are never split). Both were added to `listing-launch` v1 in place in P2-06, before any run existed.
- The staging step (`stager`, P3-04) requires `image_model`, `max_staged_images`, and `operation_kinds` (a non-empty, unique subset of `furnish`, `declutter`; v1: `[furnish]`); `max_staged_images` allows 0–10 edits per run, before integrity retries (0 turns staging off). They were added to `listing-launch` v1 in place, before any run existed (`operation_kinds` on 2026-10-29), when `image_model` moved off `creative`, which no longer accepts it.
- The integrity step (`integrity_checker`, P3-05) requires `segmentation_model`, `fixed_elements` (1–6 `{ phrase, occlusion_tolerant }`: the SAM phrase compared between original and edit, and whether staged furniture may partly hide it, which enables the containment path), `min_iou`, `min_containment`, `min_area_ratio` (each in (0, 1]), `max_aspect_ratio_change` (0–0.5), and `edit_privacy_phrases` (0–5 phrases segmented on every checked edit; any instance fails it). Phrases are `samPhraseSchema` and unique case-insensitively across both lists. v1 carries the P1-07 values (`DEFAULT_INTEGRITY_THRESHOLDS`, `DEFAULT_FIXED_ELEMENTS` in `compare.ts`, which a test pins to the YAML) and `[person]`; added in place in P3-05, before any run existed.
- `max_cost_usd_per_run` is a quoted exact decimal (`usdAmountSchema`, greater than zero). An unquoted YAML number is a float and is rejected, not coerced, so the cap reaches the ledger without a float round trip.

Market profile (`nl.v1.yaml` without comments; `international.v1.yaml` has the same shape with generic facts and bases):

```yaml
market:
  id: nl
  version: 1
  name: Netherlands
  source_languages: [nl, en]
  output_languages: [en, nl]
  default_output_language: en
  units:
    area: m2
    volume: m3
  currency: EUR
  area_bases:
    - id: NEN2580
      label: NEN 2580 usable area (gebruiksoppervlakte wonen), per the BBMI measurement instruction
    - id: cadastral
      label: Plot size as registered by the Kadaster
  facts:
    - key: energy_label
      label: Energy label (energielabel)
      type: enum
      values: [A++++, A+++, A++, A+, A, B, C, D, E, F, G]
      required: true
    - key: living_area
      label: Living area (woonoppervlakte)
      type: area
      basis: NEN2580
      required: true
    - key: volume
      label: Volume (inhoud)
      type: volume
    - key: plot_area
      label: Plot area (perceeloppervlakte)
      type: area
      basis: cadastral
    - key: build_year
      label: Build year (bouwjaar)
      type: integer
      min: 1000
      max: 2100
    - key: vve_monthly_contribution
      label: Owners' association (VvE) monthly contribution
      type: money
    - key: ground_lease
      label: Land under ground lease (erfpacht)
      type: boolean
    - key: ground_lease_annual_fee
      label: Ground lease annual fee (canon)
      type: money
  publication_checklist:
    - id: energy_label_shown
      label: The energy label class is shown in the listing
      rule: fact_present
      fact: energy_label
    - id: staging_disclosed
      label: Every virtually staged image is labeled as such
      rule: staged_images_labeled
  flagged_phrasing: [exclusionary, investment_promise, unverifiable_superlative]
  transcription_keywords: [NEN 2580, gebruiksoppervlakte, woonkamer, meterkast, vlizotrap, ...]
```

- Fact types: `enum` (`values`), `area` (`basis`), `volume`, `integer` (`min`/`max`), `money`, `boolean`. Facts are scalar so the form and the Fact Sheet stay flat; ground lease is two facts rather than an object. `required` defaults to `false`; `label` feeds the generated form.
- Area facts carry a basis listed in `area_bases`; their unit is `units.area`. Volume facts need `units.volume`, money facts need `currency`.
- Checklist rules: `fact_present` (references a known fact), `staged_images_labeled`, `no_flagged_phrasing` (category listed in `flagged_phrasing`). Phrasing categories are a closed set because the verifier implements each. Their evaluation semantics are in §5, Publication checklist (P3-07).
- Languages are known ISO 639-1 codes; `default_output_language` must be in `output_languages`. Fact keys, basis IDs, checklist IDs, and enum values are unique.
- `transcription_keywords` (optional, default empty, at most 50 unique terms of up to 64 characters): room and building terms in the source languages that bias Voice Transcribe. Fact labels contribute their parenthesised local term automatically, so it is not repeated here. Added to `nl` v1 in place in P2-06 (before any run existed); `international` v1 has none.
- `evidence_objects` (optional, default empty, at most 40): `{ id, label, phrase, supports? }` in priority order. `id` is a snake_case key (not `other`) used as the photo fact key `other:<id>`; `label` is what Spark looks for (may carry local terms); `phrase` is the SAM prompt; `supports` lists profile fact keys the object can support. IDs and phrases (case-insensitive) are unique; `supports` must name profile facts. Added to `nl` v1 (19 objects, energy label first) and `international` v1 (18, balcony/terrace → `outdoor_space`, garage → `parking`) in place in P2-08. `door` is deliberately absent (SAM matches cupboard doors, P1-05).
- The energy label classes follow RVO and the official conversion table for homes (sources cited in the YAML). A0 (zero-emission homes from 2026) is an indicator on the label, not a class.

## 8. Data model

Drizzle schema in `apps/api/src/db/schema.ts`, migrations in `apps/api/drizzle/`, repository functions in `apps/api/src/db/repositories/` (each takes the database or an open transaction, so callers compose writes and pg-boss enqueues into one transaction).

- `users`, `sessions` — single-operator accounts. Emails are stored normalized (unique on `lower(email)`); sessions are keyed by a hash of the session token, never the raw token.
- `projects` — one listing job: owner, title, office profile snapshot (JSON, zod-validated), market profile ID + version, output language, fact form values (JSON), status (`draft | active | archived`).
- `materials` — uploaded files: kind (`photo | voice_memo`), storage key (unique), MIME type, size, SHA-256, processing status (`uploaded | processing | ready | failed`), processing metadata. Size and SHA-256 describe the **stored** (processed) bytes. Metadata is zod-validated by the shapes in `packages/shared/src/materials.ts` (strict objects, so nothing unexpected is persisted):
  - `ready` photo: `{ width, height, sourceFormat: 'jpeg' | 'png' | 'webp', sourceWidth, sourceHeight }` (source dimensions after EXIF orientation).
  - `ready` voice memo: `{ durationMs, sampleRate: 16000 | 24000, sourceContainer, sourceCodec }`; `durationMs` comes from the stored WAV's samples, not the upload's header.
  - `failed`: `{ failureReason }`, a code from `MATERIAL_FAILURE_REASONS` (upload rejection codes plus `internal_error`), never decoder output or paths.
- `runs` — one execution of a service definition version: service ID + version and market profile ID + version recorded for reproducibility; status `queued → running → awaiting_gate → completed | failed`; the open gate, current step, failure reason, start/finish times.
  - Allowed transitions: `queued → running | failed`, `running → awaiting_gate | completed | failed`, `awaiting_gate → running | failed`, `failed → queued` (resume). `completed` is terminal. `transitionRun` locks the run row, rejects other transitions with a typed error, and appends a `run_status_changed` event in the same transaction.
  - Check constraints make gates real states: `gate` is set exactly when `status = 'awaiting_gate'`, and `failed` requires a failure reason.
- `run_steps` — the run engine's idempotency record (P2-03, §9): one row per run, step, and attempt (primary key `(run_id, step_id, attempt)`; the attempt increases only when a failed run resumes). Columns: status (`queued | running | completed | failed`), the pg-boss `job_id` created for the attempt in the same transaction, `job_retry_count` of the delivery holding the claim, `executions` started, an operator-safe `error`, `output_artifact_ids`, `gate_released_at` (set when the run is resumed past the step's `gate_after`), and start/finish times.
  - Partial unique indexes make the engine's guarantees database invariants: at most one `completed` attempt per run and step (`run_steps_one_completion_key`), and at most one `queued`/`running` attempt (`run_steps_one_open_attempt_key`). Checks: `finished_at` is set exactly for closed attempts, `failed` requires `error`, and a gate can only be released on a completed step.
- `run_events` — append-only event log per run, primary key `(run_id, seq)`. `seq` is gapless and strictly increasing per run: it comes from incrementing `runs.last_event_seq`, which row-locks the run, so concurrent appends serialize and commit in order. `occurred_at` defaults to `clock_timestamp()` so events in one transaction keep distinct times for replay. A trigger rejects direct UPDATE and DELETE; deletes cascading from `runs` are allowed. Event types are an app-validated text set (`RUN_EVENT_TYPES` in `packages/shared`), so new types need no migration.
- `facts` — per run: key, value (JSON), unit, measurement basis, producing step, provenance (`source_kind`: `form | transcript_turn | photo_region | gate_decision`, plus `source_ref` JSON: form field; transcript artifact ID + turn index + start/end ms + the verbatim `quote`; photo material ID + normalized region + optional mask artifact ID; or, for a value the operator entered at Gate 1, the gate + `fact_conflicts` artifact ID + conflict ID — migration `0005`, §5 Gate 1 API), status (`candidate | verified | conflicted | rejected`), assertion (`stated | opinion`, default `stated`; migration `0004`).
  - Keys are a market profile fact key or `other:<snake_case>` (non-core); area facts carry a profile basis or `unspecified`, other facts no basis (P2-07, §5).
  - The check `facts_opinion_never_verified` (`assertion = 'stated' or status <> 'verified'`) makes "an opinion is never a verified fact" a database invariant.
- `artifacts` — generated outputs per run and step: kind (open snake_case set), JSON content and/or a stored file (storage key + MIME type), and the `usage_ledger` IDs of the model calls that produced them.
  - Singleton kinds (`SINGLETON_ARTIFACT_KINDS`: `transcript`, `fact_extraction`) are unique per run, step, and kind by the partial index `artifacts_singleton_kind_key` (migration `0003`, extended in `0004`). `insertSingletonArtifact` inserts with `ON CONFLICT DO NOTHING` and returns the existing row otherwise, so a repeated commit keeps the first transcript that facts cite.
  - `transcript` content (P2-06): `transcriptArtifactContentSchema` (§5 Intake). Transcript text is personal data and cascades with the project.
  - `fact_extraction` content (P2-07): `factExtractionReportSchema` (§5 Fact extraction). Its rejected items quote model output and transcript spans, so it has the same personal-data scope.
  - `verified_fact_sheet` and `fact_conflicts` content (P2-09): `verifiedFactSheetContentSchema` and `factConflictsContentSchema` in `packages/shared/src/reconciliation.ts` (§5 Reconciliation). Values and explanations describe the property, same personal-data scope. Not singleton kinds (no migration): the step checks for an existing sheet inside the completion transaction.
  - `claim_audit` content (P3-06): `claimAuditContentSchema` in `packages/shared/src/claim-audit.ts` (§5 Verification): the passes, the remaining flags for Gate 2, the rubric. Problems and suggestions quote and rewrite copy, same personal-data scope. One per verification step, not a singleton kind (no migration): the step checks for an existing audit inside the completion transaction.
  - `listing_copy` content (P3-01): `listingCopyContentSchema` in `packages/shared/src/copy.ts` (§5 Creative copy). Copy text describes the property, same personal-data scope; its segments are also the `claims` rows. Not a singleton kind (verification adds revisions as new artifacts); the step checks for an existing copy inside the completion transaction.
  - `qa_cards` content (P3-03): `qaCardsContentSchema` in `packages/shared/src/qa.ts` (§5 Buyer Q&A cards). Questions and answers describe the property, same personal-data scope; each answer segment is also a `claims` row. Not a singleton kind (verification adds revisions); the step checks for existing cards inside the completion transaction.
  - `staged_image` (P3-04): one per staged photo, a file artifact (the staged JPEG, key `projects/<projectId>/runs/<runId>/artifacts/<uuid>.jpg`) with `stagedImageContentSchema` content (original material ID and SHA-256, declared operation, prompt, model, sizes, disclosure label); `staged_images` (P3-04): the staging step's manifest, `stagedImagesContentSchema` in `packages/shared/src/staging.ts` (§5 Staging). Staged images derive from customer photos: `deleteProject` returns their storage keys like the materials'. Not singleton kinds (no migration).
  - `approved_pack` (P3-08): written by the Gate 2 approval under step ID `gate:claim_audit`, `approvedPackContentSchema` in `packages/shared/src/gate2.ts`: the published copy segments (edits applied, removals dropped) and the staged image chosen per photo. Export's only input for decisions (§5 Gate 2 API). Copy text, same personal-data scope. Not a singleton kind (no migration): the gate is released in the same transaction, so a second one cannot be written.
  - Export (P3-09): `export_html`, `export_portal_fields`, `export_image`: one file artifact per exported file (the self-contained HTML pack, `portal-fields.json`, each published JPEG), content `exportFileContentSchema`; `export`: the step's manifest (`exportManifestContentSchema`: every file with its SHA-256, counts) in `packages/shared/src/export.ts` (§5 Export). Their IDs are content-derived (`exportArtifactId(runId, fileName)`), passed through `insertArtifact`'s optional `id`, so a rebuilt pack references the same artifacts. Copy, fact values, and customer-derived images: same personal-data scope; `deleteProject` returns their storage keys. Not singleton kinds (no migration): the step checks for an existing manifest inside the completion transaction.
  - `photo_inventory` content (P2-08): `photoInventoryContentSchema` in `packages/shared/src/vision.ts` (§5 Vision inventory): per photo the classification, cover rank, privacy results (boxes in stored-photo pixels, normalized regions, `one_bit` mask payloads), and observations with evidence regions. Model text about the property, so it cascades with the project like the transcript.
- `claims` — one row per copy segment or Q&A answer segment (P3-03; written by `storeQaCards` the same way, variant `qa` in the artifact): artifact, segment index, text, fact IDs exactly as cited (text array, no FK, so the validator can record and reject unknown IDs), validator result (`pass | fail`) + details, verifier verdict (`supported | unsupported | flagged`) + details. Written by the creative step (P3-01) for each segment of a `listing_copy` artifact, with the stored fact IDs that code mapped from the model's catalog IDs, so a stored citation is always a fact of the run; the validator result and `validator_details = { rulesVersion, findings }` are written in the same insert (P3-02). Verification (P3-06) writes the verifier verdict and `verifier_details` (`claimVerifierDetailsSchema`) on every claim of every draft it audited, the creative step's included.
- `decisions` — human gate decisions: gate (`fact_conflicts | claim_audit`), target (`fact | claim | artifact` + ID), choice (`accept | edit | remove | reject`), edited value (required exactly for `edit`), decided by, decided at. One decision per target per gate. `recordDecision` refuses unless the run is currently awaiting that gate and the target belongs to the run. `upsertDecisions` replaces earlier decisions on the same targets; its caller holds the run lock and has checked the gate (Gate 1 writes all decisions of a conflict at once, §5 Gate 1 API). Gate 2 writes one row per flagged claim (`claim`: `accept`, `edit` with `{ text, validation }`, `remove`), per offered staged image (`artifact`: `accept`, `reject`), and the sign-off (`artifact` = the `claim_audit` artifact, `accept`) (§5 Gate 2 API).
- `usage_ledger` — one row per model call: model ID, step, input/output/reasoning tokens, audio seconds (`numeric(10,3)`), images, estimated cost in USD (`numeric(12,8)`, exact decimal strings end to end — never floats), latency, run (nullable for calls outside a run).

**State columns** use Postgres enums generated from `as const` tuples in `packages/shared` (one source for the DB, API, and web; erasable-TS compatible). Open taxonomies that the pipeline extends (run event types, artifact kinds) are text validated in code.

**Deletion:** every project-derived row cascades from `projects` (and `projects` from `users`), so deleting a project hard-deletes its materials, runs, run steps, events, facts, artifacts, claims, and decisions in one statement; `deleteProject` returns the storage keys so the caller removes the files. `usage_ledger` is the exception: its `run_id` is set to NULL. Ledger rows contain no customer content (model ID, unit counts, cost, latency), and keeping them stops a deleted project from erasing spend from the global daily cap.

**Uploads and storage (P2-05, upload routes P4-03).** Code: `apps/api/src/storage/` (`Storage` interface, `createLocalStorage`), `apps/api/src/media/` (`image.ts`, `audio.ts`, `probe.ts`, plus the P1-04 `convert.ts`), `apps/api/src/upload/` (`prepare.ts`: validate and process one file into its stored form, shared with the headless CLI's `ingest.ts`; `receive.ts`: raw body → temp file; `process-upload.ts`). The HTTP routes are in the Project and input API below.

- **Storage:** `put(key, bytes | stream) → { key, sizeBytes, sha256 }`, `get(key, { range? }) → stream` (`StorageNotFoundError`; `range` = inclusive byte offsets, for HTTP Range since P4), `stat(key) → { sizeBytes }`, idempotent `delete`, `exists`. Keys are opaque and server-generated (`projects/<projectId>/materials/<uuid>.<ext>`), restricted to lower-case `/`-separated segments that cannot start with `.`, and checked again against the root after path resolution, so traversal is impossible. Writes go to `<root>/.tmp/<uuid>` (mode 0600), are fsynced, renamed into place, and the directory is fsynced: an object is either absent or complete. The local implementation is rooted at `STORAGE_DIR` (absolute; required in production, where it is the `/data` volume; `<repo>/data/storage` otherwise). `delete` removes the file permanently, which P5-04 uses with the keys `deleteProject` returns; empty directories are left in place (their names are UUIDs).
- **`processUpload({ projectId, kind, tempFilePath, clientMime?, signal? })`** (built by `createUploadProcessor({ storage, logger, capture, committer, limits? })`; `createMaterialCommitter(db, capture)` is the database side, separate so the cleanup rules are unit-tested with fakes): validate and process (`preparePhoto` / `prepareVoiceMemo`) → `storage.put` → one transaction that locks the project row, re-checks the upload rules (inputs not locked, see `inputsLocked` below; fewer than the service's maximum photos; a voice memo deletes the previous memo's row) and inserts the material as `ready` with its metadata in one insert → after the commit, the replaced memo's file is deleted. It owns the temp file and deletes it, and every intermediate file, on every path. Invalid uploads throw `UploadRejectedError` with a code (`UPLOAD_REJECTION_CODES` in `packages/shared`) and an uploader-safe message; a valid upload the project cannot take throws `UploadConflictError` (`project_not_found | inputs_locked | photo_limit_reached`). In both cases nothing stays stored and no row is written; a failure after `storage.put` deletes the file. **Ambiguous commits:** when the commit fails with anything but a definite refusal (`UploadConflictError`, an abort before the insert), the row is looked up by its storage key first: if it exists the upload stands (a replaced memo's file then stays as an orphan), if the lookup itself fails the file is kept (an orphaned file is harmless, a row without its file would break a run). Because the row is written only after processing succeeded, uploads never leave `processing` or `failed` rows (the statuses remain for other writers). At most two uploads are processed at once per process (decoding a 100 MP photo takes several hundred MB); others wait. `signal` (client disconnect) stops before storing and before the commit. `clientMime` is logged, never used for validation.
- **Photos (sharp):** limits in `UPLOAD_LIMITS` (25 MiB, 100 MP, long edge 2048 px). The container is identified by magic bytes before any decoder runs (JPEG, PNG, WebP), so libvips never parses SVG, PDF, TIFF, or GIF; sharp's header metadata must agree. The pixel count is checked on the header and enforced again by `limitInputPixels` during decoding (decompression bombs); `failOn: 'error'` rejects corrupt and truncated files. Then: auto-orient by EXIF, downscale to fit the long edge (never enlarge), flatten transparency onto white, convert to sRGB through the embedded ICC profile, and encode JPEG (quality 85, mozjpeg). sharp writes no metadata unless asked, so the output has no EXIF (incl. GPS), XMP, IPTC, comments, or ICC profile; a test builds a JPEG with GPS EXIF, XMP, orientation, and a P3 profile and checks both sharp's reader and the raw JPEG segments. **JPEG over WebP:** listing portals and every export target accept JPEG, the vision models take it, and the size difference at 2048 px is small.
- **HEIC is rejected** (`heic_not_supported`): sharp's prebuilt libvips includes libheif with the AV1 decoder only (HEVC is patent-encumbered), so it reads AVIF but not iPhone HEIC (verified in sharp 0.35.5: `sharp.format.heif` lists only `.avif`). The web app converts photos on the device during client-side downscaling (P4-03); iPhones set to "Most Compatible" upload JPEG anyway. AVIF is refused too, as it is not an accepted format.
- **Voice memos (ffmpeg):** limits 128 MiB (10 minutes of 48 kHz stereo WAV) and 600 s. `ffprobe` (argument array, `shell: false`, 15 s timeout, `-protocol_whitelist file`, `-format_whitelist` of the accepted demuxers) validates the container (MP4/M4A, WebM/Matroska, Ogg, WAV, MP3, FLAC, ADTS AAC, AMR), exactly one audio stream with an allow-listed codec, and no real video stream (cover art is allowed). A declared duration over the limit is rejected before decoding. Browser-recorded WebM declares no duration and headers can be forged, so the shared converter now takes `maxDurationMs` (ffmpeg `-t`), set to limit + 1 s: decoding work and WAV size stay bounded, and the measured WAV duration decides `too_long`. The converter also passes `-protocol_whitelist file`. The 16 kHz mono 16-bit transcription WAV is what is stored.
- **Material order:** `addMaterial` and `createRun` set `created_at = clock_timestamp()` instead of the transaction-start default. Uploads and run starts take the project lock, so material timestamps follow commit order (the photo order) and a run created right after an upload sorts after it, even when the run's transaction began first; the intake and vision steps use only materials created before their run.
- **Originals are not kept** (data minimization): they carry GPS and device metadata, and nothing downstream needs them. The trade-off is that changing processing settings later requires a re-upload.

## 9. Runs, jobs, and reliability

Code: `apps/api/src/runs/` (`engine.ts`, `queue.ts`, `steps.ts`, `worker-runtime.ts`), `apps/api/src/db/repositories/run-steps.ts`, event payloads in `packages/shared/src/run-events.ts` (P2-03).

- **Steps are jobs.** Each step attempt is one job on the pg-boss queue `run-step` (policy `exclusive`). The idempotency key `run_id:step_id:attempt` is the job's `singletonKey`, so pg-boss rejects a duplicate enqueue while the attempt's job is created, retrying, or active (`send` resolves `null`). The `run_steps` row (§8) is the authority: it records the job ID created for the attempt, and only that job may execute it.
- **Transactional enqueue.** Every state change and the enqueue it implies commit in one database transaction: jobs are sent with `boss.send(..., { db: fromDrizzle(tx, sql) })` (pg-boss 12's Drizzle adapter, verified against 12.38), so a rollback removes the job too. `startRun`, `resumeRun`, and `resumeAfterGate` accept the caller's transaction (`{ tx }`); Gate 1 (P2-10) records the last decision and resumes in one transaction; Gate 2 (P3-08) records the approval, writes the approved pack, and resumes in one. The API process enqueues through its own send-only pg-boss instance (§5 Gate 1 API).
- **What comes next is derived from the database, never from memory.** `advance` walks the definition's steps against the completed `run_steps` rows: the first completed step with an unreleased `gate_after` opens the gate (`running → awaiting_gate` plus `gate_opened`); otherwise the first step without a completed attempt is enqueued (new `run_steps` row, job, `runs.current_step_id`); otherwise the run completes. Because the gate release is stored on the step, a run that fails at a gate and is resumed stops at the same gate again.
- **Claim, execute, settle.** A delivery first _claims_ the attempt in a transaction that locks the run row and then the step row (the same order everywhere, so workers serialize per run instead of deadlocking). It is skipped without executing when the run is gone or not `running`, the job is not the attempt's job, the attempt is completed or closed, or a delivery with the same or a newer `retryCount` already holds the claim. Otherwise `executions` is incremented and `step_started` appended. The handler runs outside any transaction. On success one transaction re-checks that this delivery still holds the claim, runs the handler's `commit(tx)` (its artifacts and facts), marks the attempt completed, appends `step_completed`, and calls `advance`. A superseded execution (its claim was taken over after pg-boss expired it) therefore can neither write its output nor complete, fail, or advance the run.
- **Step contract.** Handlers are registered by `agent` (`StepHandlers`) in `createStepHandlers` (`apps/api/src/pipeline/handlers.ts`, used by `worker.ts` and the headless CLI, P3-10) (`intake` since P2-06, `extractor` since P2-07, `vision` since P2-08, `reconciler` since P2-09, `creative` since P3-01, `stager` since P3-04, `integrity_checker` since P3-05, `verifier` since P3-06, `exporter` since P3-09, `qa_writer` since P3-03), and a step whose agent has no handler fails the run with a clear reason. Handlers that need more than the context (storage, the market registry) are built by factories such as `createIntakeHandler({ storage, markets })`. `StepContext` carries the run, the service definition, the step's own typed configuration, attempt and execution numbers, the database for reads, a `StepLedger` (`meter`, `checkBudget`), a lazy `metaClients()` bound to this execution's ledger, a logger, and an `AbortSignal`. One usage ledger and one set of Meta clients are built per execution. The ledger refuses new calls after the signal aborts, and is flushed after the handler as a safety net for calls made outside `meter`.
- **Gates with nothing to decide.** `commit` may return `releaseGate: true` (P2-09): the engine then releases the step's `gate_after` in the completion transaction, before `advance`, so the run continues and a resumed run does not stop there either. The flag is ignored on steps without `gate_after`. Reconciliation sets it when there are no conflicts; verification never does (Gate 2 always needs the operator's sign-off, §5 Verification).
- **Timeouts and abort.** Each execution gets the engine's step timeout (default 10 min, configurable per step). The signal aborts on that timeout, on worker shutdown, and when pg-boss loses the job's claim. The engine stops waiting at once, even if the handler ignores the signal. The job's `expireInSeconds` is the timeout plus 60 s, so the engine always times out first. Jobs carry `heartbeatSeconds: 30`: pg-boss fails the job of a crashed worker 30 s after its last heartbeat, plus one supervise pass of up to 60 s, instead of waiting for expiry. Workers poll every 2 s, also on notify-enabled queues. NOTIFY wakes workers only for new jobs, and the 30 s default backstop would otherwise delay every retry.
- **Retry policy.** An attempt allows two executions (`MAX_STEP_EXECUTIONS`).
  - A transient failure (unknown error, timeout, interruption, a crash) puts the attempt back to `queued`, appends `step_failed` with `willRetry: true`, and throws a sanitized `StepRetryError` so pg-boss retries the job (`retryLimit: 2`, `retryDelay: 5 s`).
  - `BudgetExceededError`, `InvalidBudgetCapError`, `UnpricedModelError`, `UnpricedUsageError`, a missing definition, and `NonRetryableStepError` fail the run at once.
  - Execution setup (the step timeout and the per-execution usage ledger) fails like a handler, before the timeout timer is armed, and anything else that escapes the execution is settled the same way: no error reaches pg-boss unrecorded, where it would be redelivered until the run failed as "interrupted". An invalid budget cap is a configuration error (`InvalidBudgetCapError`, non-retryable: every attempt would fail identically). `createRunEngine` also validates `dailyCapUsd`, so api and worker refuse to start with it; the per-run cap from the definition is checked at boot by the definition schema and again per execution.
  - A second failure fails the run: `step_failed` with `willRetry: false`, open attempts closed, and `running → failed` with a reason such as `Step "b" failed after 2 executions: Step "b" timed out after 600 s`.
  - A crash counts as an execution, because the step may already have spent money. When both executions started and neither settled, the next delivery fails the run instead of executing again; the third pg-boss delivery exists for exactly that case.
  - Jobs that still exhaust pg-boss retries land in `run-step-dead`, whose handler fails the run, so a run never stays `running` without a job.
  - `resumeRun` (`failed → queued → running`) skips completed steps and gives the failed step a new attempt.
- **Operator-safe reasons.** Failure reasons, `step_failed` payloads, logs, and the error stored on the pg-boss job use the message only for errors whose text this codebase controls (timeouts, budget, pricing, `NonRetryableStepError`). Any other error is reduced to its class name (`Unexpected TypeError`), because SDK errors can carry request bodies and validation errors can quote model output.
- **Run events** for SSE and replay (payloads in `packages/shared/src/run-events.ts`, IDs, counters, and exact decimal costs only):
  - `step_started` `{ stepId, attempt, execution }`;
  - `usage_recorded` `{ stepId, stepCostUsd, runCostUsd }` after every metered call;
  - `step_completed` `{ ..., artifactIds, stepCostUsd, runCostUsd }`;
  - `step_failed` `{ ..., reason, willRetry, stepCostUsd, runCostUsd }`;
  - `gate_opened` `{ gate, stepId }`;
  - `gate_decided` `{ gate, stepId, acceptedCount, editedCount, rejectedCount, verifiedFactCount, rejectedFactCount, createdFactCount }` once, when the last Gate 1 decision releases the gate (P2-10, §5);
  - `gate_decided` for Gate 2 (a union on `gate`) `{ gate: 'claim_audit', stepId, approvedPackArtifactId, flaggedClaimCount, acceptedClaimCount, editedClaimCount, removedClaimCount, offeredImageCount, acceptedImageCount, rejectedImageCount, warningCount }` once, when the approval releases the gate (P3-08, §5);
  - `transcript_stored` `{ stepId, artifactId, mode, audioDurationMs, sourceTurnCount, turnCount, approximateTurnCount, speakerCount, keywordCount }` from the intake step's commit (counts only, never text or keywords);
  - `facts_extracted` `{ stepId, artifactId, formFactCount, modelFactCount, transcriptFactCount, opinionCount, repairedCount, rejectedCount }` from the fact extraction step's commit (counts only, never keys, values, or quotes);
  - `photos_inventoried` `{ stepId, artifactId, photoCount, classifiedCount, classificationFailedCount, privacyClearCount, privacyMaskedCount, privacyReviewCount, privacyFailedCount, privacyRegionCount, observationCount, evidenceRequestCount, evidenceMaskCount, factCount }` from the vision inventory step's commit (counts only, never subjects, summaries, or object names);
  - `facts_reconciled` `{ stepId, artifactId, conflictsArtifactId, candidateCount, verifiedCount, conflictedCount, rejectedCount, entryCount, conflictCount, basisNoteCount, model, fallbackUsed }` from the reconciliation step's commit (counts and the model ID only, never keys, values, or explanations);
  - `copy_generated` `{ stepId, artifactId, revision, outputLanguage, catalogFactCount, citedFactCount, portalSegmentCount, socialSegmentCount, claimCount, mergedUncitedCount, droppedUncitedParagraphCount, model, fallbackUsed }` from the creative step's commit (and from each revision in P3-06; counts, the language code, and the model ID only, never copy text, keys, or values);
  - `qa_cards_generated` `{ stepId, artifactId, revision, outputLanguage, catalogFactCount, citedFactCount, cardCount, segmentCount, claimCount, mergedUncitedCount, droppedCardCount, validatorResult, validatorFailedSegmentCount, validatorFindingCount, model, fallbackUsed }` from the Q&A step's commit and each Q&A revision in verification (P3-03; counts only, never questions, answers, keys, or values);
  - `claims_audited` `{ stepId, artifactId, finalDraftArtifactId, finalQaArtifactId, passCount, revisionCount, verifierCallCount, stopReason, remainingFlagCount, remainingValidatorFlagCount, remainingVerifierFlagCount, flaggedClaimCount, model, fallbackUsed }` from the verification step's commit (P3-06; counts, the stop reason, and the model ID only, never copy text, problems, or suggestions);
  - `pack_exported` `{ stepId, artifactId, imageCount, originalCount, stagedCount, blurredImageCount, blurredRegionCount, withheldCount, checklistFailCount, readyToPublish }` from the export step's commit (P3-09; counts only, never copy, fact values, or file names);
  - plus `run_status_changed` from `transitionRun`.
  - Step cost covers every ledger row of the step across attempts and executions.
- **Graceful shutdown.** On SIGTERM/SIGINT the worker stops fetching, gives in-flight steps up to 25 s to finish (a step that finishes commits its completion and enqueues the next step for another worker), then pg-boss fails and aborts what is left; those jobs are retried after restart. The database pool closes after pg-boss. A second signal terminates immediately. The compose `worker` service needs a `stop_grace_period` above 25 s; Docker's default of 10 s cuts the grace period short, and the affected steps are then recovered like a crash.
- **Database restarts.** `createDbClient` listens for `error` on the pg pool. An idle connection that the server drops (restart, admin termination, network loss) is logged by name, code, and message, never with its connection details, and the next query opens a new connection. Without the listener Node treats the event as unhandled and the API or worker process exits.
- **Proven by tests.** `apps/api/src/runs/crash.integration.test.ts` runs the real worker runtime in a child process with fake handlers. It SIGKILLs the worker during a slow step, after the first step has completed and the slow step's model call is in the ledger, and restarts it. The run then completes with each completed step executed exactly once, the interrupted step executed twice, and one ledger row per invocation; pg-boss re-delivers the job about 11 s after the kill (heartbeat 10 s in the test). The same file covers graceful shutdown. `engine.integration.test.ts` covers gates, transactional enqueue with rollback, retry and failure policy, resume, budget and timeout failures, an invalid budget cap (refused at construction; per execution, the run fails with the real reason on the first delivery), duplicate enqueues, concurrent and superseded deliveries, two workers sharing the queue, and the dead-letter handler.
- If Wonder fails, judgment steps fall back to Spark once and the result is labeled as such: reconciliation records `modelRun.fallbackFrom` on the sheet and `fallbackUsed` in its event (P2-09, §5).

**Usage ledger and budget caps (P2-04).** Code: `packages/shared/src/prices.ts` (price table, `computeCostUsd`), `packages/shared/src/decimal.ts`, `apps/api/src/usage/` (`ledger.ts`, `budget.ts`).

- **Price table:** `PRICE_TABLE` in `packages/shared`, zod-validated, keyed by model ID. Each model has one billing kind — `tokens` (`inputUsdPerToken`, `outputUsdPerToken`), `audio_seconds` (`usdPerAudioSecond`), or `images` (`usdPerImage`) — with prices as decimal strings **per single unit**, so cost = units × price is always an exact product (a per-hour price divided by 3600 is not a terminating decimal in general). A unit test pins the table to the list prices above. Cached input tokens bill at the full input rate (no discount is documented); reasoning tokens are inside `output_tokens` and are never added again.
- **Cost math:** scaled-BigInt decimals, never floats. Costs are rounded **up** to 8 fraction digits (`numeric(12,8)`), so the ledger may over-report a call by at most $0.00000001 but never under-reports spend against a cap. The meta module's `CostEstimator` keeps returning a number for display and logs (`createPriceTableCostEstimator` derives it from the same computation); the persisted cost is computed by the ledger from the units.
- **Ledger:** `createUsageLedger({ db, runId, stepId, dailyCapUsd, runCapUsd? })` implements `UsageRecorder`. It is created per step execution, together with that step's Meta clients, so entries carry the right run and step. `flush()` takes the buffer synchronously and writes it in one transaction; on a database error the entries stay buffered and `UsagePersistenceError` is thrown. `meter(modelId, call)` is how steps call models: price check → budget check → call → `flush()`, flushing also when the call throws (a call that fails on output parsing has still been billed).
- **Fail loud, not record-with-flag:** a model without a price is refused before the call (`UnpricedModelError`), so no unmetered money is spent. A completed call with missing or invalid units (e.g. the API did not report token counts) makes `flush()` persist every priceable entry and then throw `UnpricedUsageError`. Recording such a call as $0 would silently remove it from the caps, and a flag column would only move the problem to whoever reads it. A reported `0` is a real count.
- **Caps:** checked before every call; `spent >= limit` throws `BudgetExceededError { kind: 'run' | 'daily', limitUsd, spentUsd }`, which is not retryable. The run cap comes from the service definition (`budget.max_cost_usd_per_run`) through the caller. The daily cap is `DAILY_BUDGET_USD` (exact decimal; required in production, `5.00` in development/test; `0` stops all calls) and covers every ledger row in the current **UTC** day `[00:00Z, next 00:00Z)`, including calls outside runs and rows whose run was deleted. UTC rather than Europe/Amsterdam: every day is 24 hours and the boundary is independent of the server time zone.
- **Demo runs are left out of the daily cap (P4-09):** the daily total (`getCostUsdSince(…, { excludeOwnerEmail: DEMO_OWNER_EMAIL })`) skips ledger rows whose run belongs to a project of the demo owner (`usage_ledger.run_id → runs → projects.owner_id → users.email`, a `NOT EXISTS`); rows with a null `run_id` (calls outside runs, runs of deleted projects) always count. Those rows are calls `npm run demo:seed` replays from a cassette: nothing is billed, so they must not use up the live budget. The per-run cap still applies to demo runs (it sums all of the run's rows). **The ledger itself still holds the replayed usage, so any spend report built from `usage_ledger` must filter demo-owned runs the same way.**
- **Concurrency: bounded overshoot, not serialized.** The check reads committed ledger rows and reserves nothing, because a call's cost is known only after it returns; an advisory lock would serialize the check without preventing the overshoot. A cap can therefore be exceeded by the cost of the calls already in flight when it is crossed: one call for a sequential step, the step's fan-out for parallel calls (e.g. vision inventory), and across concurrent runs for the daily cap. With measured per-call costs of a few cents (more for Wonder at high effort) the overshoot stays small; the next check stops the work.

## 11. Demo replay mode

A completed run's `run_events` and artifacts are replayed in the UI with the original timing, without any model calls. The live monitor's SSE messages are the stored `run_events` rows (`runStreamEventSchema`, §5 Run API), so the replay emits the same stream from a completed run, with long gaps capped (§5 Demo API). Visitors can walk through the whole flow — gates, evidence inspector, exports — without an account. Live runs require login and an access code (§14).

- **Which runs are public:** the completed runs listed in `DEMO_RUN_IDS` (API env, comma-separated UUIDs). **Everything about a listed run becomes public without login** — photos, voice memo, transcript, facts, copy, and export — so only synthetic runs belong there. The API: §5 Demo API.
- **Making a demo run (zero model calls):** `npm run demo:seed -- [project-dir]` (default `fixtures/projects/synthetic-walkthrough`, all synthetic) runs the project through the real pipeline in fixture mode (`cli/seed.ts` on the CLI's `executePipeline`), against the configured `DATABASE_URL` and `STORAGE_DIR` instead of Testcontainers, and prints the run ID to put in `DEMO_RUN_IDS`. Every Meta request is answered from the project's cassette through MSW; an unrecorded request fails the run and any other host gets a network error, and the seed fails loudly (exit 1, nothing to publish) unless the run completed with zero live requests and nothing unmatched (the demo API would not serve a failed run anyway). No `MODEL_API_KEY` is needed or used (env role `demo-seed`).
  - **Owner:** one dedicated user `demo-replay@evidomo.invalid` (`DEMO_OWNER_EMAIL`; the Demo API serves only this user's runs, §5) with an argon2id hash of a random 32-byte password nobody knows, so it can never log in; reused on every rerun. Each run is a new project and run (rerunnable; earlier demo runs stay until their project is deleted).
  - **Isolation from the deployment's worker:** the run's pg-boss jobs go to a schema of this invocation only (`pgboss_demo_seed_<12 hex>`), dropped at the end; the production worker works the default `pgboss` schema with live clients and never sees a seed job. A crashed seed leaves its (inert) schema behind; drop it by hand.
  - **Cost accounting:** replayed calls are metered like live ones (the snapshot shows what the run would have cost, ~$0.45 for the walkthrough) but are **left out of the global daily cap** (§10), because nothing is billed: a seed never uses up the live budget, and it succeeds under a cap near zero. The per-run cap applies as usual. Only live spend already at the cap stops a seed (its pre-call check sees the live total). Spend reports from `usage_ledger` must filter demo-owned runs.
- **Tests:** `demo.integration.test.ts` (seed twice + the whole Demo API, §5) and `replay.test.ts`.
- **Web (P4-09 UI, not built yet):** public pages over the Demo API with the P4-05 monitor pointed at `demoRunEventsUrl`, and the gate, evidence, and export views fed by the demo URL builders.

- One Linode VPS in an EU region running Docker Compose: `caddy`, `web` (`next start`), `api`, `worker`, `postgres`. The API/worker image includes ffmpeg.
- Caddy terminates HTTPS automatically; the domain's DNS (Squarespace) points to the VPS.
- Firewall allows only 22, 80, 443; deploys run as a non-root user.
- Secrets live in a server-side `.env` (mode 600), never in the repository. `MODEL_API_KEY` is available only to `api` and `worker`, never to the browser.
- Deploy script: pull, build, migrate, restart, smoke test. Daily `pg_dump` to the volume.
- Images are built on the server from the repository (no registry). `apps/api/Dockerfile` builds one image for api and worker (production dependencies, sources run through type stripping, ffmpeg); its `migrate` target adds drizzle-kit for one-off migrations. `apps/web/Dockerfile` builds Next.js and runs `next start`. `infra/caddy/Dockerfile` bakes in the Caddyfile. All run as non-root users.
- `APP_ORIGIN` must be the public `https://` origin Caddy serves (api and worker refuse to start in production without it; §14).
- `infra/compose.yaml` (project `evidomo-prod`) reads variables from `infra/.env` (template: `infra/.env.example`) and passes each service only what it needs. Caddy's site address comes from `SITE_ADDRESS` (`:80` for local HTTP). PostgreSQL is not published to the host; it sits on a `backend` network with api and worker, while caddy, web, and api share an `edge` network.
- Volumes: `postgres-data`, `storage` (mounted at `/data` in api and worker, exposed as `STORAGE_DIR` for the storage interface), `caddy-data`, `caddy-config`.
- Healthchecks: postgres `pg_isready`, api `GET /api/healthz`, web `GET /`, caddy admin API. The worker has no endpoint; a fatal error exits the process and the restart policy brings it back.
- Migrations: `docker compose -f infra/compose.yaml --env-file infra/.env --profile tools run --rm migrate`.
- **Live-run access (P4-10):** `infra/compose.yaml` passes the api (only; the worker never starts runs) `LIVE_RUN_ACCESS_CODE` in the required form `${LIVE_RUN_ACCESS_CODE:?…}`, so compose refuses every command on this file while it is unset (the api would refuse to boot anyway), plus the optional `RUN_STARTS_PER_ACCOUNT_PER_DAY`, `RUN_STARTS_PER_IP_PER_DAY`, `ACCESS_CODE_FAILURES_PER_IP_PER_HOUR`, `DEMO_RUN_IDS`, and `TRUST_PROXY_HOPS` (empty means the default; `TRUST_PROXY_HOPS` 1 = Caddy). All listed in `infra/.env.example`.
- **Demo run (P4-09) on the server:** `docker compose -f infra/compose.yaml --env-file infra/.env --profile tools run --rm demo-seed`, after migrations. The `demo-seed` service (tools profile) builds the `apps/api/Dockerfile` target `demo-seed` (the api's dev dependencies for MSW, ffmpeg, `definitions/`, and the committed `fixtures/`, none of which belong in the runtime image), runs `node src/cli/demo-seed.ts` on the `backend` network with the api's `DATABASE_URL`, `DAILY_BUDGET_USD`, `APP_ORIGIN`, and the `storage` volume at `STORAGE_DIR=/data`, and gets no `MODEL_API_KEY`. It prints the run ID: set `DEMO_RUN_IDS=<id>` in `infra/.env` and restart the api (`up -d api`). Verified locally: the image builds, and the container seeded a completed run into a throwaway PostgreSQL with `DAILY_BUDGET_USD=0.01` (59 calls from the cassette, 0 live). Locally without Docker: `npm run db:up && npm run db:migrate && npm run demo:seed`.
- **Development seed (local only).** `npm run dev:seed -- --owner <email>` puts a fixture run (stopped at Gate 1, Gate 2, or completed) into the local database for an account registered in the web app, and `npm run dev:worker:replay` continues such runs after a gate decision without live calls (§5, "Development seed"). Neither belongs to a deployment: both refuse `NODE_ENV=production`, the runtime image lacks MSW and `fixtures/`, and no compose service runs them. Use `demo:seed` for the public demo run.

## 14. Security and privacy

- Uploads validated by content (magic bytes and decoder headers for photos, ffprobe for audio; never the extension or client MIME type), size, pixel count, and duration; images re-encoded with all metadata (including GPS) removed; only the processed files are stored, never the originals (§8, P2-05).
- Faces and license plates blurred in exported images by default; a photo whose privacy check is incomplete (`review`, `failed`) or whose regions cannot be read is withheld, never published unblurred, and staged images carry a burned-in "Virtually staged" label (§5 Export).
- Project deletion hard-deletes materials, artifacts, and derived data. Usage ledger rows (no customer content) are kept with their run reference cleared, so cost caps stay accurate (§8).
- No customer content is sent to Contributor-mode models or used for training/fine-tuning.
- EU hosting; data minimization by default (GDPR).

**Authentication (P4-01).** Code: `apps/api/src/auth/` (`routes.ts`, `session.ts`, `password.ts`, `tokens.ts`, `rate-limit.ts`, `config.ts`), `apps/api/src/http/` (`guards.ts`, `errors.ts`); contracts in `packages/shared/src/auth.ts` and `api-error.ts`.

- **Endpoints** (JSON, under `/api/auth`, all `Cache-Control: no-store`). Errors are `{ error: ApiErrorCode, issues? }` (`apiErrorSchema`).
  - `POST /register` `{ email, password }` → 201 `{ user: { id, email } }` and the session cookie (registration logs in). 400 `validation_failed` (with `issues`), 409 `email_taken`, 429 `rate_limited`.
  - `POST /login` `{ email, password }` → 200 `{ user }` and a fresh cookie. 401 `invalid_credentials` for an unknown email and a wrong password alike (an unknown email still runs a dummy argon2 verification, so timing does not tell them apart). 429 `rate_limited`.
  - `POST /logout` (no body) → 204, deletes the presented session row and clears the cookie; idempotent, works without a session.
  - `GET /me` → 200 `{ user }` or 401 `unauthenticated`. The web app calls it to decide whether to redirect to login.
- **Passwords:** 12–256 characters (the maximum bounds hashing cost), NFKC-normalized, hashed with argon2id m=19456 KiB, t=2, p=1 (OWASP minimum). The algorithm is the library default because the `Algorithm` const enum is not erasable under type stripping; tests assert the `$argon2id$` prefix and parameters. Login does not re-apply the length policy.
- **Emails:** trimmed and lower-cased by the shared schema and the repository. A duplicate registration returns 409, which reveals that the address has an account; accepted for a small single-operator app.
- **Sessions:** a 32-byte `crypto.randomBytes` token, base64url, lives only in the cookie; `sessions.token_hash` stores its SHA-256 (hex). Expiry is **absolute** (`SESSION_TTL_DAYS`, default 30); there is no sliding renewal or idle timeout (an idle timeout would need a `last_seen_at` column). Login and registration always issue a new token and delete the session the request presented (rotation). An expired session is rejected by the database clock, its row deleted on that request, and the cookie cleared; a successful login also sweeps all expired rows.
- **Cookie:** `HttpOnly; SameSite=Lax; Path=/`, `Max-Age` = the session lifetime. When `APP_ORIGIN` is https, the cookie is `Secure` and named `__Host-evidomo_session` (pinned to the exact host, no `Domain`); over plain http (development, a local run of the production stack) it is `evidomo_session` without `Secure`. Production refuses an http `APP_ORIGIN` other than localhost.
- **CSRF:** besides SameSite=Lax, every state-changing `/api` request (anything but GET/HEAD/OPTIONS) whose `Origin` is present and not `APP_ORIGIN`, or that carries `Sec-Fetch-Site: cross-site`, gets 403 `forbidden_origin` before its body is read. JSON routers also use `requireJsonBody`: a state-changing request with a body must be `application/json` (415 `unsupported_media_type`), which excludes what HTML forms and no-preflight `fetch` can send. Malformed JSON is 400 `invalid_json`.
- **Rate limits** (in-process fixed windows; a restart resets them; memory bounded to 10,000 keys per limiter): login 50 per IP and 10 per account (keyed by the SHA-256 of the submitted email, existing or not, so a 429 reveals nothing; reset by a successful login) per 15 minutes; registration 20 per IP per hour. 429 carries `Retry-After` in seconds. Every IP-keyed limiter (login, registration, run starts, wrong access codes, Demo API requests and streams) keys by `ipRateLimitKey(req.ip)`: an IPv4 address as is (also IPv4-mapped IPv6), an IPv6 address by its /64 prefix, because one subscriber usually controls a whole /64. A refused hit is not counted. The client IP is `req.ip` with Express `trust proxy` set to a hop count (`TRUST_PROXY_HOPS`: 1 in production, where Caddy discards client-supplied `X-Forwarded-For` and sets the real peer address; 0 elsewhere, so a direct client cannot choose its bucket).
- **Protecting routes:** `createSessionMiddleware({ db, config })` returns `requireUser` (401 `unauthenticated` JSON; the web app does the redirect) and `loadUser` (optional). Handlers read the user with `currentUser(req)` (typed `AuthUser = { id, email }`; throws, so 500, on a route not behind `requireUser`) or `optionalUser(req)`. State lives in a per-request `WeakMap`, not on an untyped `req` property. Project routes (P4-02 onwards) mount in `createApp` behind `session.requireUser` and check `projects.owner_id` against `currentUser(req).id`.
- **Logging:** user IDs only, never emails, passwords, tokens, cookies, or IPs. The HTTP error handler logs body-parser errors by type only (they carry the raw body) and reduces database errors to the SQL text and PostgreSQL code (`errorForLog`), because Drizzle's `DrizzleQueryError` embeds every bound parameter in its message.
- **Live-run access control (P4-10)** (`projects/run-start-guards.ts`, wired through `AppProjectDeps.runStartGuards`, §8 "Start a run"). Registration is public on the deployment; an account alone cannot start a live run.
  - **Access code:** `LIVE_RUN_ACCESS_CODE`, required for the api in production (`loadEnv(…, 'api')` refuses to boot without it; development and test may leave it unset, and then starting a run needs only a session and any sent `accessCode` is ignored). 12–256 characters, no surrounding whitespace; generate one with `openssl rand -base64 18` and share it with the people allowed to run live. Compared in constant time: SHA-256 of both sides, then `timingSafeEqual` on the 32-byte digests, so neither length nor a matching prefix shows in the timing; the configured code is kept only as its hash. Never logged (the boot log says only whether a code is set; refusals log the user ID).
  - **Errors:** a **missing** and a **wrong** code both answer **403 `access_code_invalid`**: the request is authenticated but not permitted, and one code tells the UI "show (or correct) the code field" in both cases; a 400 would make the code look like a schema field whose requirement depends on server config (`accessCode` stays optional in the schema). A malformed `accessCode` (not a string, empty after trimming, over 256) is 400 `validation_failed`, whose issues never echo the value.
  - **Wrong codes per IP:** `ACCESS_CODE_FAILURES_PER_IP_PER_HOUR` (default 10). Each submitted code is counted before it is compared and refunded when right, so only wrong codes count and a blocked IP gets 429 `rate_limited` (`Retry-After`) even for the right code (no oracle). A missing code is no guess and does not count. With 10 guesses per hour per IP and a 12+ character random code, online guessing is impractical.
  - **Run starts:** `RUN_STARTS_PER_ACCOUNT_PER_DAY` (default 3) per user ID and `RUN_STARTS_PER_IP_PER_DAY` (default 5) per client IP, 24-hour fixed windows, both checked after the code (a wrong code uses no allowance). Over either: 429 **`run_limit_reached`** with `Retry-After` (a separate code from `rate_limited`, so the UI can say "today's live runs are used up" rather than "slow down"). Only starts that started a run count: a hit is reserved before the handler (so concurrent starts cannot overshoot) and refunded when the response is not 201 (`not_ready`, `run_active`, `daily_budget_reached`, a 500), never when the client disconnects first (the run may have started). The limiter's `refund(key, windowResetAt)` only touches the window the hit was counted in.
  - **Global daily cap:** unchanged and still enforced at start (409 `daily_budget_reached`, §8) and before every model call mid-run (`createUsageLedger` → `checkBudget`, `BudgetExceededError` is non-retryable and fails the run; `usage/ledger.integration.test.ts` "stops work at the global daily cap").
  - In-process like the login limits: one API instance, a restart resets the counters (bounded to 10,000 keys per limiter). A refused hit is not counted (the window holds allowed hits only), so a refund after refusals always frees a real slot. Tests: `run-start-guards.test.ts` (correct, wrong, missing, not configured, malformed, the wrong-code limit, both run limits, refunds, no code in logs) and `projects.integration.test.ts` (the guards in front of the real route).
- **Web side** (`apps/web/src/lib/auth.ts`, `components/AuthGate.tsx`, `pages/login.tsx`, `pages/register.tsx`):
  - `useMe()` (TanStack Query on `GET /api/auth/me`) is the only source of "who is signed in", because the cookie is httpOnly. A 401 resolves to `null`, not an error, so it is never retried; other 4xx are not retried either, network failures and 5xx twice. Login and register mutations write the returned user into the `me` cache; logout navigates to `/` first and then sets `me` to `null` and drops every other cached query.
  - Every response is parsed with the shared schemas (`authUserResponseSchema`, `apiErrorSchema`) by a small fetch helper (`lib/api.ts`, `credentials: 'same-origin'`, JSON `Content-Type` only on requests with a body). Errors become `ApiRequestError { status, code, issues, retryAfterSeconds }`; forms map `validation_failed` issues to fields by `path[0]`, `invalid_credentials` to one generic message, `email_taken` to an inline message with a login link, and `rate_limited` to the `Retry-After` wait.
  - **Guards** are opt-in per page: `Page.auth = 'required'` (signed-in only) or `'guest'` (login, register), read in `_app` by `AuthGate`; pages without the flag are public, which keeps the demo replay (§11) open to visitors. `required` renders a session check while `me` loads, never the content, and on `null` calls `router.replace('/login?next=<asPath>')` once the router is ready. `guest` sends a signed-in user to `next`, which also completes a successful login or registration. This is client-side gating for the user experience only; `requireUser` on the API is the enforcement.
  - **`next` validation** (`lib/next-path.ts`, prevents an open redirect): a string of at most 2,048 characters that starts with exactly one `/`, contains no backslash, control, or whitespace character (browsers turn `/\host` and `/<TAB>/host` into `//host`), resolves to the same origin, and is not `/login` or `/register`. Anything else falls back to `/`.
  - `/projects` is the protected signed-in landing page (an empty state until P4-02).
- **Environment:** `APP_ORIGIN` (the browser-facing origin, e.g. `https://evidomo.example`; default `http://localhost:3000`, required in production), `SESSION_TTL_DAYS` (1–365, default 30), `TRUST_PROXY_HOPS` (0–5; default 1 in production, 0 elsewhere), `LIVE_RUN_ACCESS_CODE` (api only, required in production), `RUN_STARTS_PER_ACCOUNT_PER_DAY` (default 3), `RUN_STARTS_PER_IP_PER_DAY` (default 5), `ACCESS_CODE_FAILURES_PER_IP_PER_HOUR` (default 10), `DEMO_RUN_IDS` (§11; default empty). `loadEnv(source, role)` applies per-process production rules: `worker` (default) and `api` need `MODEL_API_KEY`, `api` also the access code, `demo-seed` neither.
